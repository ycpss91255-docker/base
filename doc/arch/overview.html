4. 生成 Pipeline

從人工編輯的 config 到 Docker-native 輸出的完整流程。觸發點：just setup、init.sh（見 sec. 7）或 upgrade（見 sec. 8）。

5. Host / Container 邊界

TOML 解析工具（已決）: 獨立 toml-bridge container image（dockerfile/Dockerfile.toml-bridge），內含 alpine + Python 3 + vendored tomli（PEP 680 backport）。Host 不安裝 Python 或任何額外工具。test-tools 透過 COPY --from 取得 TOML 能力，downstream repo 經 test-tools-stage 繼承。

6. Dockerfile Stageflow

TOML 解析能力透過 image 繼承鏈傳遞到所有 repo。toml-bridge 是獨立的 Dockerfile，test-tools 用 COPY --from 取得它的產物，downstream repo 再透過既有的 test-tools-stage pattern 繼承全部工具。

7. init.sh 流程

Downstream repo 首次 bootstrap 或 .base 升級後 resync 的入口。觸發：just setup、just base init、upgrade Step 3。 核心工作：偵測新/舊 repo → 執行 migration → 呼叫 sec. 4 的 generation pipeline。

8. upgrade 流程

Downstream repo 升級 .base subtree 到新版本。觸發：just base upgrade [vX.Y.Z]。 關鍵設計：Step 3 執行的是新拉下來的 init.sh（不是舊版），所以所有 migration 和 config 重生都跑最新邏輯。

9. ADR-36 整合

ADR-36 將 sec. 4 的整個生成 pipeline 封裝為可被外部呼叫的 API。Orchestrator 不直接碰 config 檔案，只提供路徑和輸出目錄，呼叫 generate API，拿到 Docker-native 輸出。

這個分層決定了 TOML 遷移的爆炸半徑：format 變更被限制在 generate API 內部，orchestrator 完全無感。

10. 模組總覽

Base repo 的腳本分成兩大群組：出貨到下游（透過 .base/ subtree 傳遞，約 27,100 行）和 base 專屬（測試、CI、版本監控、發版，約 23,100 行）。合計約 50,200 行 shell script，另有 90,400 行測試 spec（183 檔 bats：158 unit / 21 integration / 4 system）。出貨與 base 專屬比例約 54:46，測試密度 1.8 行 spec / 1 行 shipped code。

出貨到下游的程式碼分四層：Wrapper（7 檔，使用者操作入口：build / run / setup / exec / stop / prune + 凍結中的 setup_tui）、Lib（31 檔，核心程式庫透過 _lib.sh 傘狀載入 21 模組）、Lifecycle（init.sh / upgrade.sh，獨立進入不經 wrapper）、Runtime（4 檔，容器內執行：entrypoint / watchdog / logging / logrotate）。

Base 專屬的程式碼分四區：Test Framework（test.sh dispatcher + 28 driver lints）、CI（ci-and-stamp.sh + GitHub Actions workflows）、Watch（版本監控，pin 文法 + resolver）、Release（release-tag.sh + changelog.sh）。

11. 目錄架構

Base repo 的檔案分兩大區：dist/ 是出貨到下游的內容（透過 .base/ subtree 傳遞），其餘為 base 自用。dist/script/docker/ 下是容器操作的核心程式碼（wrapper → lib → runtime 三層）；dist/script/base/ 是生命週期腳本（init / upgrade）。Base 專屬腳本在頂層 script/，測試 spec 在 test/bats/（按 ISTQB level 分目錄），文件在 doc/。
