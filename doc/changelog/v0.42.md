## [v0.42.0-rc4] - 2026-08-25

### Fixed
- **nine more early-closing readers, and the class that inverted the answer rather than losing it (closes #905)** -- #898 fixed one `| sort | head` that died 141 under `pipefail`; confirming it turned up nine more instances of the same mechanism, one class of which is worse than the bug that was fixed. A reader that stops reading (`grep -q` leaves on its first match, `head -n1` after one line) strands a writer that is still writing: SIGPIPE, exit 141, `pipefail` promotes 141 to the PIPELINE's status, and an `if` reads that as false. **A successful match is reported as "not found"** -- the status is not lost, it is inverted, and nothing fails loudly; the caller simply takes the other branch. Whether the race is lost is environment-dependent, measured during #898 at **0 failures in 20000 host iterations** (glibc, bash 5.1) against **6.4% inside the alpine test-tools image** (musl, coreutils 9.5, bash 5.2), so "I ran it and it was fine" is not evidence here -- and five of these ship in `dist/`, which every downstream repo executes on whatever host it has. **Class B, the inverted answer (5 sites).** `run.sh`'s already-running guard reported a LIVE container as not running and started a second one over it, instead of refusing; `exec.sh` took the same test negated and refused a container that WAS running, telling the user to start it; `detect_gpu` reported an installed `nvidia-container-toolkit` as missing, so `setup` wrote a GPU-less `.env` on a GPU host; `completions.sh` re-printed the `fpath` hint for a directory already on `$fpath`; and the base-version monitor's dedupe gate read an already-open tracking issue as absent and filed a duplicate -- weekly, in every downstream repo, until someone upgraded. **Class A, the status thrown away (3 sites).** `upgrade.sh:_get_latest_version`, `init.sh:_detect_template_version` and `gitignore.sh:_prune_retired_entries` each met the abort and answered with `|| true`, which stops the crash by discarding the status -- including a genuine failure of the pipeline -- and leaves a quieter defect: an EMPTY answer that reads as a legitimate "nothing found" (no newer release when there is one; a repo stamped with no template version; a retired entry never retracted from the downstream `.gitignore` the template was trying to clean). #898 deliberately did not take that route, and neither does this. **Class C (1 site).** `_tui_conf.sh:_detect_mig` had no suppression at all: 141 straight out of a bare assignment. The live caller is `if _detect_mig; then`, and `if` suspends errexit for the whole function body, so it misreported rather than aborting -- a MIG-enabled host told it had no slices, withholding the UUIDs the user needs for `NVIDIA_VISIBLE_DEVICES`; called outside a condition the same 141 kills setup outright (pinned at status 141, no output). **Every fix removes the dependency rather than the symptom**: each site drains its stream with a `while IFS= read -r` loop over a process substitution and compares in-shell, so no exit status depends on how two processes were scheduled. No `|| true` survives and `pipefail` is untouched. `run.sh` and `exec.sh` asked the identical question with the identical spelling, so the probe is hoisted to `lib/wrapper.sh:_wrapper_container_running`, the module that already owns what the five docker wrappers share. Dropping `grep -oP` from the two tag scans also drops a PCRE dependency that does not exist on a BSD / macOS host, where both had been silently returning `""` behind the `|| true`. **Testing is deterministic, not repeated**: two shared helpers in `test/bats/unit/test_helper.bash` pin the losing interleaving with PATH shims -- a reader that exits without reading a byte, a writer that writes only after it has gone -- so a reintroduced pipeline fails on EVERY run instead of a few percent, the technique `adr_numbering_spec` established in #898. Nine specs gained a case (`run_sh` 67, `exec_sh` 58, `setup_detect` 50, `completions` 14, `base_version_monitor` 13, `upgrade` 48, `init` 53, `gitignore` 47, `tui` 135). `upgrade_spec`'s errexit/pipefail case is rewritten rather than deleted -- it pinned a real contract (rc=0 and an empty answer on an unreachable remote, so `_check`'s guard is what reports it) while describing `|| true` as the mechanism -- and its strict shell became a script FILE, which un-skips it under `COVERAGE`: `bash -c '...'` leaves `${BASH_SOURCE}` empty at top level, so kcov's `PS4` killed it under `set -u` before the code ran, and it had been skipping in precisely the environment where this defect reproduces. **Recurrence guard, with the false-positive count measured before building it.** A naive whole-tree rule is worthless: bats test bodies run with errexit ON and pipefail OFF (measured -- `false | true` yields 0 there), so all ~65 `| head` / `| grep -q` lines under `test/bats/**` are structurally incapable of the inversion, giving ~65 candidates and 0 true positives. Scoped to `dist/` + `script/`, the shell that actually runs under `set -euo pipefail`, the same rule flagged **exactly the nine defects and nothing else** -- and replaying it over every release from v0.30.0 to v0.41.0 flags the same six lines (the nine, before the tree was reorganised) and never anything else, i.e. **zero false positives across twelve releases**. That is the opposite of #895's rejected rule (68 candidates, ~11 true positives, >80% false positive), so this one is built: new `early-close-reader` lint (`script/test/drivers/early_close_reader.sh`, `just test lint --early-close-reader`, `test.sh --early-close-reader-only`, CI job `lint-static (early-close-reader)`), with a region-delimited `# early-close-lint: allow-begin/allow-end` opt-out (no live region today) and a no-vacuous-pass scan-root check. It deliberately does NOT flag a reader that drains (`grep -v`, `grep -c`, which `build.sh` / `prune.sh` / `setup_tui.sh` use), `grep -q` with a file operand, `||`, a here-string, or a comment describing the shape. Its stated limitation: `sed 1q` and `awk 'NR==1{exit}'` also stop reading, but the tree has no instances, and widening to shapes with no instances would trade a measured zero false-positive rate for guesswork. `self_test_yaml_spec`'s `_LINT_TOOLS` completeness guard rises 9 -> 10 and pins the new name; new `early_close_reader_lint_spec.bats` (20). Closes #905.

The base-version monitor's `BASE_REPO` / `MONITOR_LABEL` / `BASE_VERSION_FILE` are documented in CONTEXT.md beside the monitor (including that `BASE_REPO` also names the release link the monitor publishes into a real issue, and that `MONITOR_LABEL` is half the dedupe pair). `SYSTEM_DOCKER_SOCK` is documented in `doc/test/system.md` as the supported way to point the system level at another daemon -- the issue proposed removing it as callerless, which is wrong: `_system_setup` probes it, and the two prerequisite-guard specs depend on it for the per-test isolation that fixed their race (#816). `QUIET` is documented in `build.sh` / `run.sh` `--help` in all four locales, including that it is a different knob from `setup.sh`'s `-q/--quiet`. **Privatised**: the five `TUI_*` knobs (geometry + button captions) are `_TUI_*` internals of the backend wrapper, and the geometry is now a constant, so `TUI_WIDTH=0` can no longer reach `dialog(1)` unvalidated; `VERBOSE` in `stop.sh`, an ambient input created only by a missing `local`, is declared like every sibling flag, so `-v` is the one way to switch the teardown listing on. **Removed**: the `:-1000` fallback for `HOST_UID` / `HOST_GID` in `compose.yaml` -- on any host whose developer is not uid 1000 it left the files the suite wrote into the bind-mounted checkout owned by a stranger, silently. The issue said `just test` always supplies them; it does not, and neither did CI: `just test system` and self-test.yaml's system job drive `docker compose run --rm ci-system` directly, and test.sh passed the ids with `-e` (which sets them *inside* the container) while compose's own `${HOST_UID}` interpolation reads the *caller's* environment. All three now export them, an unset value is refused by name, and a non-numeric one is refused by `_fix_permissions` before it reaches `chown`. Removing the default also makes the ids required of commands that name a service reading neither, because compose interpolates the WHOLE file whatever service is named -- `just docker build --target test-tools` (base's documented self-use of the docker namespace, and the first thing `just test system` runs) was refused, by a message naming `just test`. base's own root `justfile` therefore exports them once, which `just` propagates into every module recipe, so the whole `just` surface resolves and raw `docker compose` stays the only refused path; the paths also reachable via `just -f` (the `system` recipe, `test.sh`) keep setting them for themselves.
- **every name CI creates is now keyed to the run that created it, and every run hands its artifacts back (closes #900)** — the local half of this was already fixed: #892 keyed the test-tools tag to its build inputs and the compose project to the checkout path, and #893 resolved one `PROJECT_NAME` both the wrapper's `-p` and the emitted `compose.yaml` read. On a RUNNER both discriminators are constant. The checkout path is always `/home/runner/work/<repo>/<repo>`, and every run of one commit resolves the same content hash, so `test-tools:local` (loaded with `load: true` in five jobs), the compose project, and the acceptance job's scaffolded `e2e_test` consumer are the SAME names in every concurrent run. Nothing collides today only because `runs-on: ubuntu-latest` hands each job a fresh single-tenant VM — and this repo is moving to self-hosted runners (ADR-00000008 carries the amendment, `coverage-gate` calls itself the self-hosted coverage-floor gate, #766 is the stated prerequisite). The key is `${{ github.run_id }}-${{ github.run_attempt }}`, set **unconditionally** in ONE workflow-level `env:` block that feeds all three surfaces: `TEST_TOOLS_IMAGE`, `COMPOSE_PROJECT_NAME`, and `CI_RUN_KEY` for the acceptance scaffold's directory name (whose basename becomes `IMAGE_NAME`, hence the image tag, the container name and the project). Not a timestamp (two jobs starting in the same second collide, and it cannot be traced back to a run) and **not the commit SHA** (shared by every job of a run and identical across a re-run — precisely when a stale leftover would be reused). Costs nothing in build cache: buildx reuse is keyed by `cache-from` / `cache-to` scope, not by the image tag. **Cleanup is the other half.** A unique name per run means leftovers accumulate on a long-lived host instead of dying with the VM, and the obvious collector — `docker system prune -a` — is actively harmful on exactly that machine, because a shared host's "unused" resources include a concurrent job's in-flight cache and images. New `script/ci/reclaim.sh` removes only what a run can PROVE it created, by label (`base.ci.run=<key>`, stamped on every path that loads a test-tools image, including the pulled-and-retagged hot path) or by a name embedding `ci-<key>` (the scaffolded consumer's artifacts, which downstream tooling names but base does not build). Two layers in one `if: always()` teardown step per docker-using job: `--run` is exact and is the normal path; `--stale 12h` is the backstop for the case `--run` cannot cover at all, a runner killed before its teardown ran. **12h, not prune.sh's local defaults** (networks 10m, images 24h): an artifact belonging to a live run can be as old as the longest a job may run, and GitHub's per-job ceiling is 6h, so the window has to sit above that ceiling or the sweep deletes work in flight. The classes with no ownership marker (dangling images, unattached networks, buildx cache) are delegated to the sibling `prune.sh`, whose docker prune verbs skip in-use resources by definition. Volumes are removed by the exact layer only — age is no evidence of ownership for a resource holding state. **Downstream** rides the reusable-workflow half: `build-worker.yaml` keys its generated `WS_PATH` to the run and reclaims through the same version-matched `.worker-base` checkout the cache-scope script uses, so callers inherit it by bumping the ref they already pin — the generated `main.yaml` caller is untouched and needs no per-repo edit. ShellCheck's base-own pass was rooted one level up (`script/` rather than `script/test/`) in the same change: `script/ci/` had been outside every lint pass.
- **the ADR-numbering lint no longer dies of SIGPIPE and silently withholds the local-CI stamp (closes #898)** — `script/test/drivers/adr_numbering.sh` computed the ADR number range as `printf '%s\n' "${_nums[@]}" | sort | head -n1`. `head` closes the pipe the moment it has its line; a `sort` that has not written yet takes SIGPIPE and dies 141, `pipefail` promotes that to the pipeline's status, and the bare assignment under `set -e` kills the whole lint phase. Measured in the test-tools image (bash 5.2.37 / GNU coreutils 9.5 on musl) the race is lost in 326 of 5000 runs — 6.5%, always as `PIPESTATUS=0 141 0`. What failed was therefore not a test but the **stamp**: `ci-and-stamp.sh` reported `rc=141 action=no-stamp`, the marker was not written and `gh pr create` was denied, telling the operator local CI had not passed when every check in fact had, and teaching a retry-until-green habit. The min/max scan is now in-shell (`(( 10#${_n} < 10#${_min} ))` over the array that already exists), so the lint has no pipeline whose exit status depends on a reader that stops reading. `sort`/`tail` are gone with it; a numbering gap is still advisory-only. Separately, `_run_lint_tool` now arms an ERR trap (`-E`, since an ERR trap is not inherited by shell functions) that reports the tool, the failing command and the status through the new registered `ci_lint_driver_failed` event, decoding an above-128 status into its signal — so the next unexplained driver abort says `lint tool 'adr-numbering' stopped at ..., status 141 (killed by signal 13/SIGPIPE)` instead of surfacing as a bare number that reads like a lint finding. errexit is deliberately untouched: the driver still stops at its first failing command, since running it under `|| _rc=$?` would disable errexit inside the whole driver and let a real failure sail past. Regression cover is deterministic rather than 6.5%-of-the-time — `adr_numbering_spec` pins the losing interleaving with PATH shims (a `head` that closes without reading, a `sort` that writes late) so a reintroduced pipeline fails on every run, and `ci_spec` covers the abort report for both a signalled and an unsignalled driver failure.
- **the tag `docker compose build test-tools` writes is now the tag `docker compose run ci` reads, because neither has a default to diverge on (closes #896)** — `compose.yaml` read ONE variable with TWO different fallbacks: the build-only `test-tools` service fell back to `test-tools:local`, while the `ci` / `coverage` / `ci-system` consumers fell back to the published `ghcr.io/ycpss91255-docker/test-tools:latest`. Edit `dockerfile/Dockerfile.test-tools`, `docker compose build test-tools`, `docker compose run ci`, and the suite runs against the OLD published image with the fresh local build sitting unused — nothing warns. It fires exactly when someone drives compose directly, which is what a person debugging the tooling does (it happened during #869). The file's own header asserted the opposite ("the tag comes from the SAME `TEST_TOOLS_IMAGE`"). **Giving all four the same default was rejected**: it removes the divergence and keeps the failure mode — a bare compose run would still quietly build or pull something instead of saying the operator left the entry point. So there is **no default at all**: each service is `${TEST_TOOLS_IMAGE:?set by 'just test' / 'just docker build --target test-tools' -- run one of those instead of driving docker compose directly}`, compose's own error form, which refuses the whole invocation and names the recipe. With no default there is nothing to diverge, by construction. This is the same rule ADR-00000003 already applied to the consumer compose ("bare `docker compose up` support is dropped"), now applied to base's own. **Consequence — every `just` path sets it.** `script/test/test.sh`'s `_run_via_compose` (the one function behind every `just test` form: bare, `lint`, `coverage`, `coverage-shard`, `bats-*`, `--bats-path`) resolves it through the existing `_resolve_test_tools_image` and EXPORTS it — compose reads the value while interpolating on the HOST, so `-e` would not have reached it. That moves the local default from the rolling published tag to the content hash of this checkout's tooling Dockerfile, and the published tag is measurably stale (the `:latest` on the development host carries neither kcov nor `docker compose`), which is the same staleness behind the #869 false green. New `_ensure_test_tools_image` therefore builds that tag when the host lacks it, through the SAME compose service the docker namespace builds — a local-only tag that is absent means "not built yet", never "pull it" — and leaves a caller-pinned value alone, because provisioning that is the caller's job. `just docker build --target test-tools` relied on the removed `test-tools:local` fallback; `dist/script/docker/wrapper/build.sh` now resolves it for a **self-managed repo** (no `.base/` subtree, ADR-00000011 sec.4, where there is no pinned base version to scope a local tag by) by asking that repo's own `script/test/test.sh --test-tools-image` rather than deriving a second tag — two derivations that agree by luck is the defect, so there is one derivation and one value. The resolved tag is forwarded on both channels a repo can read it through: the `--build-arg` a consumer Dockerfile's `FROM ${TEST_TOOLS_IMAGE}` consumes, and the exported environment a self-managed `compose.yaml` interpolates, where a `--build-arg` never reaches. Repos WITH a `.base/` subtree keep the version-scoped `.base/.version` derivation untouched. **CI verified, not assumed**: every `TEST_TOOLS_IMAGE` occurrence in the tree was enumerated — `self-test.yaml` sets it explicitly in the 6 jobs that reach these services (`hadolint`, `bats-fragile`, `bats-integration`, `coverage`, `acceptance`, `system`), and `build-worker.yaml` / `publish-worker.yaml` / `release-test-tools.yaml` pin version-scoped GHCR tags through the build-arg channel into a DOWNSTREAM repo's Dockerfile, never through this compose file; the `system` job's direct `docker compose run --rm ci-system` pins it too. Nothing CI pins changed. New integration spec `compose_test_tools_image_spec.bats` (3) drives `docker compose config --images` — what compose actually resolves, not what the file's text says — comparing the build side against each consumer and pinning the refusal message; `ci_spec.bats` (84 -> 88), `build_sh_spec.bats` (54 -> 57) and `base_docker_namespace_spec.bats` cover the resolution, the ensure-built rule and the self-managed branch. - **two concurrent self-test runs no longer share one tooling image tag and one compose project by accident (closes #891)** — `compose.yaml` pinned `image: test-tools:local` on the build-only `test-tools` service and `just test system` pinned `TEST_TOOLS_IMAGE=test-tools:local` on the consumer side, so every checkout on a host wrote and read one tag; and `script/test/test.sh` invoked `docker compose run` with no `-p`, so compose fell back to the checkout DIRECTORY BASENAME for the project name. Both collisions are silent. A sibling run rebuilding the shared tag displaces the image a live run is already using with no error at all — kcov vanished from the image mid-pass during #869 and the pass still reported green, which means a coverage run can report clean having never run kcov — and two checkouts at `~/a/base` and `~/b/base` reuse each other's containers and network, worktrees staying isolated today only by the accident of being named apart. **Image:** the local default is now `test-tools:<12 hex of sha256 of dockerfile/Dockerfile.test-tools>` (`test.sh --test-tools-image`). Content, not commit or run id: a per-commit tag would rebuild an image whose inputs did not change, whereas keying on content means two runs on the same inputs SHARE the image (correct, and a cache hit) while any difference produces a tag that cannot clobber — exactly what would have prevented the #869 incident, since the sibling was building different inputs. The tooling Dockerfile is the image's only input: the service passes `context: .` but the Dockerfile never reads it (every COPY is `COPY --from=<stage>`, no ADD), so hashing the context would churn the tag on every unrelated source edit and defeat the cache while changing nothing about the image; tool versions live inside the file, so an upgrade does move the tag. The digest is the whole file rather than the stage-list projection `_compute_dockerfile_hash` takes — that hash answers "did the set of compose services change?" and must ignore RUN lines, and a RUN line is precisely what dropped kcov. The build-only service now reads the SAME `TEST_TOOLS_IMAGE` its `ci` / `ci-system` / `coverage` consumers read, so what the build writes and what the consumers resolve cannot diverge (that divergence is silent — the consumers would quietly pull the published image while the local build sat unused), and a missing tooling Dockerfile fails loud instead of falling back to the bare literal. **Project:** `_run_via_compose` passes `-p` explicitly, defaulting to `base-<12 hex of sha256 of the ABSOLUTE repo root path>`, and the `system` recipe exports the same name for its own `docker compose run`. Keyed to the path, not the commit, because two worktrees are routinely branched from the same commit — a commit-keyed name would collide in exactly the concurrent case this separates — and the path is stable across commits, so a checkout keeps one project instead of churning a network per commit. Hashed rather than sanitised because compose accepts only `[a-z0-9][a-z0-9_-]*` while a path may hold spaces, uppercase, punctuation, non-ASCII or a leading dot: a constant prefix plus hex digits satisfies the grammar by construction for any input. **Overrides are untouched:** `TEST_TOOLS_IMAGE` and `COMPOSE_PROJECT_NAME` still win verbatim, so the version-scoped GHCR tags pinned by `build-worker.yaml` / `publish-worker.yaml` / `release-test-tools.yaml` and `self-test.yaml`'s explicit `test-tools:local` all flow through unchanged — the derivations are LOCAL defaults only. Fail-loud guards keep the isolation from degrading silently (an unusable digest dies instead of collapsing to the bare `base-` prefix every checkout would share). Unit-tested in `ci_spec.bats` (71 -> 84) and `base_docker_namespace_spec.bats` (5 -> 8), including a hostile checkout path and a cache-reuse case; verified locally that two consecutive builds resolved `test-tools:4f04591c8021` with the second fully CACHED at an unchanged image ID, while appending one line to the tooling Dockerfile moved the tag. Closes #891.
- **one shared matcher decides which line declares a build stage, so `FROM --platform=... AS <stage>` is no longer half-visible (closes #875)** — five readers of a Dockerfile's stage list answered "which line is stage `<S>`'s FROM line" with three different regexes. Four demanded exactly one token between `FROM` and `AS`; `_bake_config_copy` used a greedy `.*`. On the standard cross-build form this repo actively invites (`TARGETARCH`, the arm64 matrix) — `FROM --platform=$BUILDPLATFORM ubuntu:24.04 AS runtime` — the strict four saw nothing and the loose one matched, and every consequence was silent: no compose service (`compose_emit.sh`'s emit loop is fed by `_parse_dockerfile_stages`, and its only warning path fires solely when the user also wrote a `[stage:<name>]` section), no drift detection (the hash projection uses the same shape, so adding or removing such a stage never moved the hash), no per-stage TUI override menu, and — the compounding one — a field bundle carrying the baked `config/app` and **none** of the `[environment]` defaults, because the ENV bake returned 1 while the config splice matched, and `docker build --target runtime` still succeeded so the bundle shipped. `_dockerfile_stage_from_line` (`lib/stage.sh`) is now the single answer, routed through by `_parse_dockerfile_stages`, `_compute_dockerfile_hash`, `_generate_runtime_dockerfile`, `_bake_config_copy` and the TUI's `_list_dockerfile_stages_available` (which stops carrying a private copy and sources `stage.sh`). Its accepted grammar is **stated, not inferred from a regex**: `FROM [--flag[=value]]... <image-ref> AS <stage>`, uppercase `FROM` / `AS`, zero or more leading `--`-prefixed flag tokens, exactly one image reference which may not start with `-`, one stage token, trailing whitespace tolerated, any `#` disqualifying. Widening for flags deliberately did **not** inherit the rest of what the greedy form tolerated: `FROM img junk AS x`, `FROM img # note AS x` and a repeated `AS` are all lines `docker build` itself rejects, and `_bake_config_copy` no longer splices into them. `_generate_runtime_dockerfile` also stops conflating two different non-results — exit **1** stays the silent "nothing to bake" (no Dockerfile, or an empty `[environment]`), while a stage the Dockerfile does not declare is now exit **2** plus a `deploy_stage_absent` WARN naming the stage and the file, so a deploy asking for a stage that does not exist is named instead of quietly producing a bundle missing its env. The regression guard is an **agreement** spec, not five more per-function tests — per-function tests are exactly the shape that let the matchers drift, since each only ever exercised its own regex: `stage_spec.bats` (84 -> 94) drives every call site off one FROM line and asserts a single verdict token per site, across the flagged, multi-flag, plain, lowercase-`as`, commented-out, stray-token and inline-`#` cases; `tui_flow_spec.bats` (105 -> 106) covers the fifth reader.

- **convention: bake self-built artifacts at `/opt`, not under `$HOME` -- stated where authors meet it, and gated (closes #799; ADR-00000024)** -- the container user is baked at BUILD time (`sys` takes `USER_NAME` / `USER_UID` / `USER_GID`, `devel` then sets `ENV HOME="/home/${USER_NAME}"`), so `$HOME` is frozen to whichever user the build received -- `just build` injects the local host's user, CI and release bake `user` (UID 1000). Anything an image bakes **under `$HOME`** is therefore coupled to the build-time username, and it only bites at deploy time: run a prebuilt / GHCR / `docker save`+`load` image under a different `USER_NAME`, or rebuild with one, and every home-relative path resolves to a different, EMPTY home tree -- the baked workspace is invisible and `source ~/some_ws/install/setup.bash` fails. An absolute `/opt/...` path is immune because there is no `$HOME` indirection left to resolve. The convention: (1) self-built artifacts (colcon workspaces, SDKs, compiled tools) install at absolute `/opt/<name>`, `$HOME` reserved for dotfiles and convenience symlinks; (2) the entrypoint / bashrc sources the **absolute** path, never `~` / `$HOME` -- a `~/<name> -> /opt/<name>` symlink in the per-user `RUN` block is encouraged for interactive discoverability but must never be what anything *sources*; (3) no concrete username in a path, use `${HOME}` / `${USER_NAME}`. The filename is now CANONICALISED before it becomes part of the key: the canonical name is the LONGEST filename in the report set of which it is a path suffix, matched on `/` component boundaries. The aliases are pure prefix truncations of one another, so this is exact and needs no filesystem access. Basename-only keying is explicitly rejected — distinct files legitimately share a basename (`dist/script/docker/lib/deploy.sh` and the generated field launcher `deploy.sh`) and merging them would silently OVERSTATE coverage. Observations are collected on the raw filename in a single pass and re-keyed at `END`, since the canonical map is only knowable once every filename in the set has been seen; the helper stays self-contained (no `_die` / `_log_*`), so the standalone CI CLI and the sourced driver still share it. The gate additionally reports the collapsed-alias count on stderr — always, including `0` — so a future regression in kcov's path reporting moves a visible number instead of failing silently. `COVERAGE_MIN` is deliberately unchanged: the rate rises once aliases stop being double-counted, and re-basing the floor belongs to a follow-up now that the measurement is correct. - **generic single-service watchdog: supervised restart with a pluggable health check (closes #797, ADR-00000020)** — a third `[lifecycle]` capability base owns, sibling to restart (#478) and init (#792): a health-check-driven watchdog for the container's one service. It is GENERIC — the app supplies the health-check COMMAND (`watchdog_check`, whose exit status is the health signal) and base ships the supervision loop (`runtime/watchdog.sh`, a new sourced entrypoint helper next to `logging.sh`/`logrotate.sh`). EVERY knob defaults OFF: with `watchdog_check` empty (the master switch) there is no watchdog and no behavior change, so the entrypoint's `. /usr/local/lib/base/watchdog.sh` line is a safe no-op (default compose is byte-identical — the #505 golden is unaffected). After `watchdog_start_period`, the check runs every `watchdog_interval`s (bounded by `watchdog_timeout`); after `watchdog_failures` consecutive failures the `watchdog_on_fail` action fires: `restart-container` (DEFAULT, Docker-native) exits the container so the restart policy restarts it (Docker's backoff absorbs storms), or `restart-service` restarts only the in-container service in place — supervising it as a `setsid` PROCESS-GROUP LEADER and stopping/restarting the WHOLE group like `docker stop` (bounded SIGTERM → grace → SIGKILL) so the service AND every grandchild it spawned die on each restart (no orphaned subtree leaks; `init = true` reaps dead children but does not kill live orphans — the process-group kill is what prevents the leak), trapping SIGTERM to forward a graceful stop on `docker stop`, counting restarts and GIVING UP LOUDLY at `watchdog_max_restarts` — running the optional `watchdog_notify` command then falling back to exiting the container (SIGTERM to PID 1 -> tini forwards it to the service and exits, tearing the container down; the supervisor's interval waits are interruptible so a `docker stop` SIGTERM is forwarded to the service at once, never deferred until the next interval). Watchdog events always log loudly to stderr (`docker logs`), and when `[logging] local_path` is on they also write a `watchdog.log` under the log dir's `watchdog/` subdir (per-start file + stable symlink + retention, reusing `logrotate.sh`). - **`[lifecycle] init` toggle — Docker init / PID1 reaper, default ON (closes #792)** — a new `[lifecycle] init` key makes `compose_emit.sh` emit `init: true` on the service, running Docker's daemon init (`docker-init` = tini) as PID 1 to reap zombies and forward signals. "Default ON" is enforced at both layers: the seeded `setup.conf` ships `init = true`, and the code-level key-absent fallback in `_resolve_deploy_context` (`deploy.sh`) resolves to `true`, so an existing downstream that regenerates (or a conf missing the key) also gets it. - **reusable build/release workers self-validate the caller contract before doing any real work (closes #800)** — a downstream repo's CI is a thin caller that hands work to base's shared `build-worker.yaml` / `release-worker.yaml`, which need the caller's `main.yaml` to supply required inputs (`image_name` / `archive_name_prefix`) and permissions (a future registry-cache backend needs `packages: write`). When a caller omitted one, nothing surfaced it up front: CI either 403'd at the final push after ~20 minutes or silently skipped a step and stayed green — the same drift class as the v0.41 Dockerfile drift. The workers now run a preflight step BEFORE any build/archive work that never fails silently. - **keep `host` as the network default, ship `bridge` as a usable opt-in (closes #794, ADR-00000019)** — issue #794 originally proposed flipping the `[network]` default to `bridge` / `ipc = private` on least-privilege grounds; empirical testing (`RESULTS.md`) reversed that. - **conf.sh INI writers + upgrade.sh rollback: destructive error paths guarded (#700)** — a strengthened adversarial test-audit round found two verified destructive-failure modes. The `_resolve_deploy_context` resolve-once + both-renderer dedup (the #563 core) and the remaining list-reader migrations follow. Unit-tested in `test/unit/conf_accessor_spec.bats`. Refs #563, #564.
- **`conf.sh` opaque accessor interface (#564, architecture deepening)** — new read-side accessor verbs hide `conf.sh`'s internal parallel-array representation and the `<section>.<key>` namespacing rule so callers query setup.conf without knowing the data model: `_conf_load <file> <handle>` tokenizes a file once into a named handle; `_conf_get <handle> <section> <key> [default]` returns a value (last occurrence wins) or the default; `_conf_sections <handle>` lists section names in first-appearance order; `_conf_list <handle> <section>` lists a section's keys in file order (for iterating list sections like `volumes mount_*` / `environment env_*`). Caller adoption lands incrementally starting with the resolved-config seam (#563), which restructures the prime adoption site (`_resolve_deploy_context`) — migrating those call sites now would be churn #563 immediately rewrites. Unit-tested in `test/unit/conf_accessor_spec.bats`. Refs #564, #563.

- **`release-test-tools.yaml` arm64 leg moved off QEMU to a native-runner matrix with push-by-digest manifest merge (#587)** — the test-tools publish workflow emulated arm64 via `docker/setup-qemu-action` on a single `ubuntu-latest` runner (`platforms: linux/amd64,linux/arm64`, one `push: true` producing a correct-but-slow manifest), while `build-worker.yaml` / `publish-worker.yaml` had already moved to native runners. It now builds each arch on its native runner (`linux/amd64` -> `ubuntu-latest`, `linux/arm64` -> `ubuntu-24.04-arm`) via a `compute-matrix` -> `build` -> `merge` pipeline and drops the QEMU step. **Crucially, the multi-arch contract is preserved correctly:** each `build` shard pushes its single-arch image *by digest* (`outputs: ...,push-by-digest=true`, no tag), and a `merge` job assembles the tagged manifest list with `docker buildx imagetools create`. This deliberately does **not** mirror `publish-worker.yaml`'s pattern of each shard pushing the *same tag* — that leaves a last-shard-wins single-arch tag, which for the test-tools image (consumed by every downstream `FROM ${TEST_TOOLS_IMAGE}`) would break CI on the losing arch. (`publish-worker.yaml` carries that latent single-arch bug; tracked separately.) Verified structurally by `release_test_tools_yaml_spec.bats` (+4) and `actionlint`; the live multi-arch publish is exercised by the actual workflow run. Closes #587.
- **setup.conf section list made a single source in `lib/schema.sh` (`SCHEMA_SECTIONS` + accessors, #561, schema epic #559 phase 2)** — phase 1 (#560) unified per-key *validation*; the *section list* was still duplicated as hardcoded alternations (`setup.sh`'s `_setup_known_section` case and `setup_tui.sh`'s `main` CLI direct-jump subcommand list). This adds `SCHEMA_SECTIONS` (the ordered 14-section list, matching the `setup.conf` template header order) plus two accessors to `schema.sh`: `_schema_is_section <section>` (membership predicate) and `_schema_section_keys <section> <outarray>` (a section's registered keys, derived from `SCHEMA_VALIDATOR` by canonical-key prefix). `_setup_known_section` now derives from `_schema_is_section` (keeping the per-service `[logging.<svc>]` shape as the one explicit special case the registry does not model), and `setup_tui.sh`'s CLI subcommand recognition routes through a new `_tui_known_subcommand` (any schema section, plus the `ports` pseudo-section) -- so adding a section to the registry makes it known to `set`/`add` and usable as `setup_tui.sh <section>` automatically. This also closes the latent gap where `lifecycle` / `additional_contexts` / `logging` had editors but were unreachable as direct subcommands. **Deliberately out of scope** (kept explicit): the TUI's four grouped menu dispatches stay per-menu (they are #221 UX grouping guards, not a global section list -- the `*_no_longer_dispatches` regression tests enforce that each menu only acts on its own sections), and `_resolve_deploy_context`'s section-load stays a deliberate 10-section subset (a full `SCHEMA_SECTIONS` loop would change which sections the deploy resolver reads). Full menu-metadata-ization (group / order / label columns) is a future follow-up. `_schema_section_keys`'s first non-test consumer is the #562 coverage test. Behaviour-preserving (full gate green); new tests in `schema_spec.bats` (+10), `setup_spec.bats` (+2), `tui_flow.bats` (+4). Refs #561, #559, #560.
- **setup.conf validation unified behind a single registry (`lib/schema.sh` + `_schema_validate`, #560, schema epic #559 phase 1)** — validation for "is this `<section>.<key> = <value>` valid?" was wired twice: setup.sh's `_setup_validate_kv` (a per-section `case`) and the TUI's per-call-site validator names threaded through `_edit_list_section` / inline scalar editors. The two could (and did) drift. This introduces `script/docker/lib/schema.sh` -- a flat dotted-key registry (`SCHEMA_VALIDATOR` mapping a canonical `<section>.<key>` to the validator function name that still lives in `_tui_conf.sh`; `SCHEMA_EMPTY` for the empty-value policy) plus one dispatcher `_schema_validate <section> <key> <value>` that normalises per-service `[logging.<svc>]` sections and numbered list keys (`port_3` -> `port_`) before lookup. Both paths now route through it: `_setup_validate_kv` collapses to a one-line adapter, and the TUI's `_edit_list_entry` / `_edit_list_section` drop their validator parameter while every scalar / logging editor calls `_schema_validate` keyed by `(section, key)`. schema.sh joins the `_lib.sh` chain (and setup_tui.sh's). **Behavioural consequence -- the rule sets are now the union:** keys the TUI already validated but setup.sh's `set` / `add` historically accepted as free-form are now rejected by `set` / `add` too: `build.target_arch`, `build.network`, `build.arg_*`, `deploy.gpu_runtime` (+ legacy `runtime` alias), `network.network_name`, `devices.device_*`, `security.cap_add_*` / `cap_drop_*`. Only previously-invalid values are affected; a valid `setup.conf` is unchanged, and compose / `.env` output is byte-identical (full gate green: 1676 unit + 74 integration). The registry's `kind` / `default` / `i18n` columns and section enumeration are deferred to phase 2 (#561), where dispatch / menu / section-load derivation will consume them. New `test/unit/schema_spec.bats` (14). Refs #560, #559.
- **per-service compose emitter extracted from the `generate_compose_yaml` god-function (#566, architecture deepening)** — the ~1015-line `generate_compose_yaml` (29 positional args, ~16 nested emitter closures, and the per-stage service loop all in one scope) is split into a thin orchestrator plus testable seams. The per-stage loop body becomes a top-level `_emit_stage_service <ctx> <resolved> <svc> <emit_stage> <has_overrides>` that consumes one **resolved-stage value** (the `_dflags_eff` record from `_resolve_docker_flags`) plus a shared static context and emits a single service YAML fragment -- either the zero-diff `extends: devel` shape (no overrides) or the standalone block (overrides, which compose `extends` cannot express because it merges lists). The ~16 leaf emitters (`_emit_caps_block`, `_emit_gpu_deploy_block`, `_emit_logging_block`, `_logging_svc_local_path_mount`, `_emit_target_arch_line`, ...) are hoisted to top level as shared sub-seams taking their context explicitly instead of closing over the 29 args; the dead `_emit_logging_local_path_volume` (defined, never called) is removed. `generate_compose_yaml` now orchestrates: parse stages, emit header / devel baseline / top-level `volumes:` + `networks:`, and per stage load+filter `[stage:*]` overrides, resolve them, and hand the resolved value to the emitter -- shrinking from ~1015 to ~449 lines. Behaviour is byte-identical: the full-file golden master (`compose_gen` #85) and all 113 compose specs stay green, and `compose_emitter_spec.bats` (27 tests) now exercises each emitter in isolation instead of grepping the whole generator's output. The devel baseline block stays in the orchestrator by design (it is the `extends:` target, not a looped stage; folding it in would risk byte-drift for no locality gain). Refs #566, #505, #563.
