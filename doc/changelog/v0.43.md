## [Unreleased]

### Added

- **the required-kill mutation roster runs everywhere (closes #1461)** --
  `just test mutation-required` reads every row of
  `script/test/mutation_required/*.tsv` (`<id> <subject> <spec> <old>
  <new>`, three escapes), validates all rows before any baseline, probes
  each in its own sandbox copy and compose project, four at a time, and
  passes only when every row is PINNED. The S1b/S1d/S1h rows move from
  `sed -i` commands to literal old/new (#1476) and S1a adds two seeds.
  The no-flag `just test` runs it between lint and bats; each hosted
  lint-static leg and the self-hosted config-gen job run the recipe.

- **the config generator's mutation baseline is decided on the host
  (closes #1464)** -- `just test go` first runs
  `script/test/config_gen_mutation_targets.sh`, which writes a manifest of
  the Go files changed since the base (the merge-base with origin/main, or
  HEAD^1 when `CONFIG_GEN_MUTATION_CONTEXT=main-push`) plus hashes of the
  module's visible and ignored files, and hands them to the build as the
  `mutation` context. A shallow clone, a missing ref or a bad override is
  refused by name, never reported as no change. Both CI workflows set the
  context; local runs and the pre-PR mirror default to pr.

- **the config generator image is provisioned by digest (closes
  #1466)** -- `lib/config_gen.sh` adds `config_gen_resolve`, which names
  the image `config-gen:<12 hex>` over `Dockerfile.config-gen` and its
  build context `dockerfile/config-gen`, builds `--target final` once
  when it is absent, and memoises it in `_CONFIG_GEN_RESOLVED` without
  printing. `CONFIG_GEN_IMAGE` wins verbatim with no docker call; a
  failed build, a missing subtree input and a host without docker each
  refuse by name and return 1. The resolve/ensure/build steps move into
  `lib/tool_image.sh`, shared with the TOML bridge, whose functions are
  now wrappers with unchanged behaviour.

- **the config generator's Go gates run in every environment (closes
  #1462)** -- a stdlib-only module at `dockerfile/config-gen/` (command
  registry, exit 0/1/2/4) and `dockerfile/Dockerfile.config-gen`, whose
  test stage runs fmt, vet, golangci-lint, `go test -race` and a >= 90%
  per-package coverage floor, one RUN each. `just test go` runs them,
  holds the scratch binary to rc 2 / empty stdout, then plants one
  defect per gate and requires each to go red. The hosted `config-gen`
  job (in ci-rollup and release), the self-hosted job and the pre-PR
  mirror all run that one command; specs pin both workflows' frames.

- **one coverage verdict for local, GitHub-hosted and self-hosted runs
  (closes #1411)** -- `coverage_gate.sh --verdict <manifest> <run-dir>...`
  runs the COVERAGE_MIN floor (one report per run directory) and the
  run-manifest union check together. The hosted coverage-gate job, the
  self-hosted `coverage-local.yaml` (which ran the floor only), the new
  `just test coverage-gate` recipe (local had no verdict) and the pre-PR
  mirror's coverage-gate leg (its own floor and union steps) all end with
  it. `coverage_gate_spec.bats` and `pre_pr_mirror_parity_spec.bats` fail
  if they drift -- in the invocation, a floor-only or union-only call
  beside it, the manifest each reads, or a COVERAGE_MIN override.

### Fixed

- **every JSON log record named log.sh as its source (refs #1464)** --
  `code.filepath` and `code.lineno` were read one stack frame too shallow,
  so each record pointed at the `_log_<level>` wrapper inside
  `dist/script/docker/lib/log.sh`. They now name the script and line that
  called `_log_<level>`.

- **the pre-PR mirror attested jobs it never ran (closes #1409)** -- it
  was untracked, ran bats plain where CI gates on kcov, and skipped
  `system` and `acceptance`. Now `script/ci/pre_pr_mirror.sh` marks every
  `ci-rollup` need attested or excluded; on a code change it runs every
  shard of CI's coverage matrix as CI does, then coverage-gate's steps,
  and `just test acceptance`, and `just test system` when
  `system_paths.sh` matches, a moved file counting at both ends as in
  CI's pathspec diffs. A spec holds the plan to each job's `if:`, the run
  to the plan, and modes to CI's. Acceptance steps moved into
  `script/ci/acceptance.sh`.
- **CI ran the shellcheck, doc-counts and lint-static jobs on the ubuntu
  host while the local gate ran them in the test-tools image (closes
  #1412)** -- the jobs now run `test.sh --lint --shellcheck`,
  `--lint --doc-counts` and the new `--lint --group N/T` in the image,
  and the shellcheck job installs no tarball. The host `--<tool>-only`
  arms stay for operators, but the lint dispatch refuses a CI runner's
  host (`ci_host_lint_on_runner`). The parity spec runs every `test.sh`
  step per matrix leg and runtime value with a stub `docker`, and holds
  each lint job to its own lint.
- **A weighted coverage shard ran the prev-release spec with no fixture
  (closes #1433)** -- the host decided whether a `--coverage-shard`
  needed `.prev-release/` from the checkout's weights, while the
  container partitioned by the forwarded `SHARD_WEIGHTS_BLOB`; a blob
  that moved the spec to another shard left that shard without it. The
  host now partitions by the same blob, in CI and with
  `--shard-weights`.

- **bats-integration timed out on the 4-core hosted runner (closes
  #1429)** -- the integration suite ran at 32 jobs on 4 cores, which
  stretched its slowest tests past the 120 s per-test bound. It now runs
  under a `cpu-bound` jobs policy, `max(cores, 8)`, in CI and in
  `just test bats-path` on an integration path. Unit, fragile and shard
  runs keep `max(cores, 32)`; the 120 s bound is unchanged.

- **`just test coverage N/T` did not run CI's shard N/T (closes #1410)**
  -- its weights, weight keys and slice count each differed. Weights are
  keyed by repo-relative path, so the five basenames shared by a unit and
  an integration spec carry their own runtimes.
  `just test coverage N/T <weights>` partitions by the file compute-shards
  publishes as the `shard-weights` artifact, decoded as CI decodes it;
  with no weights, or an empty file, a shard weighs by `@test` count as
  CI's cache-miss shards do, never by the checkout's `.shard-weights`. A
  shard runs `COVERAGE_JOBS` kcov slices (default 4, the hosted runner's
  cores), and CI sets it explicitly.

- **no bats test had a timeout, so a hang named no test in CI and
  blocked a local run (closes #1413)** -- the driver exports
  `BATS_TEST_TIMEOUT` on every bats run: 120 s plain, 3x under kcov,
  set by `PER_TEST_TIMEOUT`, which `just test` forwards into the
  container. The CI kcov steps get a step `timeout-minutes` below the
  job's (15/60, 75/90). The compose run behind `just test` runs under
  `timeout --foreground` (120m, 360m for coverage, `SUITE_TIMEOUT`) and
  logs `ci_suite_timeout`; `just test stop` removes the container it
  can leave. test-tools patches bats 1.13.0, where a failing test kept
  its timeout watchdog alive and the run waited the whole timeout.

- **a coverage shard ran its bats jobs under one kcov, which lost
  covered lines and printed trace fragments to the step output (closes
  #1414)** -- `_run_coverage` and `_run_coverage_path` run each job's
  slice as a serial bats under its own kcov and join the slices with
  `kcov --merge`. Slice work dirs are mode 0755, slice stderr goes to a
  file with a bounded tail replayed, and an empty selection prints
  `1..0`. test-tools builds kcov v43 with upstream 76bf685 backported
  and retries apk. The 1 MiB value test runs under kcov again.

- **a directory in place of `setup.toml` was applied as an absent layer
  (closes #1400)** -- `setup.sh apply` exited 0 and wrote its outputs. It
  now exits 1 with `conf_toml_merge_failed` naming the path; a FIFO or
  device layer is refused with `merge_layer_not_regular` before it is
  opened, where a FIFO used to hang. `toml_bridge_building` now goes to
  stderr, not the parse's stdout, and the config summary refuses an
  unparseable `setup.toml` before printing anything. Config refusal specs
  assert status, empty stdout, event id and path; `apply` is covered on
  CRLF, non-ASCII, invalid UTF-8, 1 MiB values and unreadable layers.

- **a `setup.toml` that failed to parse was reported as one with no keys
  (closes #1398)** -- `_load_setup_conf_full` dropped the tokenizer's
  status, so `setup remove` on a malformed file logged
  `conf_key_not_found`; the config summary printed an empty section, or
  for a file with no header it recognised the "no section overrides"
  hint, with rc 0. `_load_setup_conf_full` now returns 1 with its arrays
  empty, `setup remove` exits 1, and `_print_config_summary` parses every
  existing `setup.toml` first and returns 1 on a failed parse, each
  logging `conf_toml_parse_failed`. A valid, comments-only or absent
  file still returns 0.

- **the INI-to-TOML migration committed a `setup.toml` the load refuses
  (closes #1397)** -- the migration's commit gate parsed the converted
  file in the bridge's JSON mode, while the load reads `setup.toml` with
  `--kv`. A conversion such as `[x]` / `volume = [{a = 1}]` passed the
  gate and was committed, and the next load refused it ("x.volume is an
  array, and no numbered family ... carries an array"). The gate now
  parses with `--kv`: such a file is declined with
  `ini_to_toml_migration_declined` naming `x.volume`, `setup.toml` is not
  written, the temp file is removed and the source is not renamed. Files
  the load accepts still commit.
- **the config summary showed an unknown array as valid (closes #1396)**
  -- `toml_bridge.py --entries`, the summary's read of `setup.toml`,
  skipped an array of scalars (`[x] arr = ["a"]` printed nothing, exit 0)
  and printed a root or table array no numbered family carries
  (`[[install]]`, `[[build.install]]`) as rows, while `--kv` refuses the
  same file. `--entries` now refuses it with the `--kv` message naming
  the array's dotted path, exit 1 and nothing on stdout, through one
  check both views share; the summary prints no setup.toml rows for such
  a file.

## [v0.43.0-rc5] - 2026-10-21

### Fixed

- **no record froze the worker filenames a consumer's `main.yaml` names
  (closes #1203)** -- `init.sh` writes `main.yaml` once and `upgrade.sh`
  rewrites only the `@ref` of its `uses:` lines, so renaming
  `build-worker.yaml`, `release-worker.yaml`, `publish-worker.yaml` or
  `multi-distro-build-worker.yaml` inside base would strand every consumer
  that calls it. ADR-00000006 now lists the four as protocol-stable, and
  `init_spec.bats` fails if a worker the generated `main.yaml` names, or any
  file under `.github/workflows/` declaring `workflow_call:` (`.yml` or
  `.yaml`), is missing from that list. No worker is renamed.

- **the deploy-scoped restart policy landed on `test-tools-stage` (closes
  #1325)** -- `setup.sh apply` over the template Dockerfile gave the
  `test-tools-stage` service `restart: unless-stopped`, and `setup.sh
  deploy --stage test-tools-stage` was not refused and went on to build it. The stage only
  supplies tooling to the `*-test` stages, so `_is_deployable_stage` now rejects it
  like `sys` / `devel-base`: no `restart:` on it, and deploy refuses it as
  not a deployable stage. Deployable stages keep their policy. The
  `[lifecycle] restart` migration notice names it as excluded.

- **a refused apply left a half-written set (closes #1270)** --
  `setup.sh apply` over `[deploy] gpu_capabilities = ""` wrote three env
  files, then aborted with `6: parameter null or not set` and no
  `compose.yaml`. apply now stages all four files and moves them into
  place only after every emitter succeeds: a refusal leaves the previous
  set byte-identical (none on a first apply), a target or existing
  `.env.local` that is not a regular file is refused, and a move failing
  part-way restores the rest. An empty `deploy.gpu_capabilities` /
  `deploy.gpu_count` is refused naming the key and its conf file. An
  existing `.env.local` is never rewritten.

## [v0.43.0-rc4] - 2026-10-20

### Fixed

- **a repo with no commits died with no structured log record (closes
  #1385)** -- `upgrade.sh` run in a git repository with no commits yet
  (unborn HEAD) passed the repository preflight, then died on
  `git rev-parse HEAD` with only git's own error and exit 128. It now
  refuses such a repo in the upgrade preflight, before the subtree is
  touched, and logs `upgrade_no_commits`; the exit code is 1.
- **a missing subtree root exited with no structured log record (closes
  #1382)** -- when `upgrade.sh` could not find the `.version` + `dist/`
  subtree root above itself, it printed a plain-text line before its
  logger was loaded, so a `LOG_FORMAT=json` run got no record. It now
  logs `upgrade_subtree_root_not_found` as an ERROR record, through
  `log.sh` when it sits beside the script and as a minimal hand-written
  record (no code location, thread id or trace context)
  when it does not; the exit code stays 1.
- **a rollback left behind upgrade-created files whose names git quotes
  (closes #1381)** -- the pre-upgrade untracked snapshot and the rollback
  sweep read `git ls-files` line by line, so a name holding a tab, a
  newline, a quote, a backslash or a non-ASCII byte arrived in git's
  C-quoted form and `rm -f` was handed a path that does not exist. Both now
  read a NUL-delimited `git ls-files -z` listing, so such files the upgrade
  created are removed and the user's own are kept.
- **a failed pre-upgrade untracked-file snapshot let the upgrade carry
  on (closes #1384)** -- if `git ls-files` failed while `upgrade.sh`
  recorded the untracked files, the snapshot was left empty and the
  upgrade pulled anyway; a later rollback then deleted the user's own
  untracked files. The upgrade now stops before the subtree pull and
  logs `upgrade_untracked_snapshot_failed`.
- **every fatal `upgrade.sh` error logged the event body
  `upgrade_rollback`, rolled back or not (closes #1369)** -- each fatal
  path now logs a body naming what failed, such as
  `upgrade_fetch_failed`, `upgrade_unknown_arg`,
  `upgrade_not_a_git_repo` or `upgrade_subtree_pull_failed`.
  `upgrade_rollback` is logged only after the repo has been restored;
  a restore in progress logs `upgrade_rollback_started`, a failed one
  (the reset failed, or an upgrade-created file could not be listed or
  removed) `upgrade_rollback_failed`, and an aborted conflicted merge
  `upgrade_merge_aborted`.
- **`setup.sh add` / `set` wrote a key `apply` then refused (closes #1374)**
  -- `add build.args MYARG=1` (the family is `build.arg`) appended
  `args_1` to setup.toml, and `set deploy.gpu_cuont 1` wrote `gpu_cuont`;
  both exited 0 and the next `apply` refused the file with
  `apply_unknown_key`. `set` now checks the key, and `add` the family, with
  the same `_setup_known_key` apply uses, and refuses an unknown one with
  exit 2 and "unknown key <section>.<key>; no reader reads it" (log event
  `conf_unknown_key`) before writing; setup.toml, or setup.local.toml with
  `--local`, is left byte-identical. Values and the numbered
  `<list>_N` addresses are unchanged.
- **`setup.sh --help` named the INI key `[volumes] mount_1` (closes #1373)**
  -- the `-o, --output DIR` help said an apply that would have to rewrite
  "a stale absolute [volumes] mount_1" is refused, a key setup.toml never
  holds. It now says "a stale absolute source in the first `[[volumes]]`
  entry", the way setup.toml reads, in every `--lang`; the setup.sh header
  comment uses the same terms. Help text only; the numbered
  `volumes.mount_*` CLI addresses are unchanged.
- **Dockerfile migration notices printed twice in one upgrade (closes #1372)**
  -- `upgrade.sh` reached the migration dispatcher twice, once through the
  `init.sh` its Step 3 re-runs and again at its own Step 5, and each
  "Dockerfile unchanged" warning, the `ENTRYPOINT ["/entrypoint.sh"]`
  advisory and the `Dockerfile migrations:` summary came out on both
  passes. `init.sh` now records that it ran the dispatcher, and Step 5
  skips its own pass when it did, so each notice prints once per run. An
  upgrade driven by an older vendored `upgrade.sh` and a standalone
  `just base init` still apply and report the migrations.
- **`just base update` exited 0 when the version check failed (closes #1370)**
  -- `upgrade.sh --check` now exits 2 when the check itself fails (any
  fatal error: the remote cannot be fetched, a sourced helper is missing,
  `WRAPPER_TRANSCRIPT` is refused, a command stops the script), a code
  above 2 passes through, and `just base update` exits with that code. "Update available", "up to date" and "ahead" still exit 0
  through the recipe; `--check` still exits 1 for "update available". A
  normal `upgrade.sh` run keeps its exit codes.
- **a successful upgrade left only an unfinished `log/upgrade/<ts>.log.raw`
  (closes #1371)** -- both a successful and a rolled-back `upgrade.sh`
  run now finish their transcript: `log/upgrade/<ts>.log` ends with
  `transcript_complete exit_code=.. duration=..` and `latest.log` points
  at it. The rollback still restores the repo; it now runs as an
  `_atexit` callback instead of replacing the transcript's EXIT trap.
  A rolled-back run exits with the failing step's own code, and a
  rollback whose `git reset --hard` fails still prints `rollback FAILED`,
  exits 1 and finalizes the transcript.
- **every upgrade log line, warnings included, carried the event body
  `upgrade_started` (closes #1364)** -- only the `Upgrading: X -> Y` line
  is `upgrade_started` now. The other `upgrade.sh` lines log as
  `upgrade_step`, `upgrade_completed`, the version-check events and the
  config / setup.toml drift events; the Dockerfile migration notices log
  as `dockerfile_patched`, `entrypoint_patched`, `dockerfile_unchanged`
  (the ARG USER notices included), `dockerfile_needs_manual_fix` and the
  entrypoint advisories. Display text is unchanged.
- **warnings and a generated comment named old INI keys setup.toml does
  not have (closes #1365)** -- the ports-inert warning now names
  `[[network.ports]]` instead of `[network] port_*` in every locale; the
  `.env.generated` comment over extra build args says
  `(from [[build.args]])` instead of `(from [build] arg_N)`; and the
  stale workspace-path warning names the first `[[volumes]]` entry
  (`volumes.mount_1`) instead of `[volumes] mount_1`.
- **`setup.sh remove` added blank lines and reordered keys in `setup.toml`
  on every call (closes #1363)** -- `remove` now changes only the removed
  entry and keeps `x = []` lines in place. A table `add` creates carries
  the header comment `# added by setup add; removed with its last entry`
  and goes again with its last entry; an empty table you wrote stays. A
  `x = []` that `add` fills stays on its line as a comment, and the
  `remove` that empties the list puts it back as it was. An add/remove
  round trip of one value gives back the same file and the same
  `SETUP_CONF_HASH` in every case the regression specs cover.
- **shipped text told the consumer to run `./build.sh`, `./run.sh`,
  `./stop.sh`, `./setup.sh` or `./setup_tui.sh` at the repo root (closes
  #1357)** -- a consumer has them only as `./script/<name>.sh`. The
  compose.yaml header and init.sh's setup warning now say
  `just docker setup apply`; the wrapper hints, the config summary, the
  rename warnings, the upgrade next step, the README Quick Start, the TUI
  notices and the Dockerfile comments name `just docker ...`. The
  derived-figures lint now fails on a root-relative `./<wrapper>.sh` in
  emitted or shipped text, `--help` text and `dist/.setup.conf` aside.
- **every rewrite of a user-owned file left it at mode 0600 (closes
  #1356)** -- `setup.sh set` / `add` / `remove`, the TUI save, the
  `mount_1` bootstrap, the stale workspace-path rewrite and the v0.42
  `lifecycle_restart_default` migration rewrote `setup.toml`, and pruning
  a retired entry rewrote `.gitignore` / `.dockerignore`, each from a 0600
  `mktemp` file. The rewrite now takes the file's own mode before it
  lands, and a `setup.toml` created by the write gets the mode any new
  file gets under the caller's umask. If the mode cannot be set, the
  file is left unchanged and the write reports an error. A file an
  earlier run already left at 0600 is not repaired.
- **`setup help` and the `add` / `remove` confirmation named `<list>_N`
  keys setup.toml does not hold (closes #1354)** -- the help now says
  `volumes.mount`, `network.port` and `devices.cgroup_rule` append a
  `[[volumes]]`, `[[network.ports]]` or `[[devices.cgroup_rules]]` entry
  and only `environment.env` writes an `env_N` key. The confirmation names
  the entry as the file spells it, e.g. `[setup] add [[volumes]] source =
  "/foo", target = "/bar"`, read from the file: a `[[tmpfs]]` entry with
  separate `path` and `size` fields is printed with both.
- **generated `.env` / `.env.local` / `config/.gitkeep` text, the
  migration notices and `just --list docker` said a bare
  `just docker setup` regenerates `.env`, but a bare `setup` only prints
  its help (closes #1355)** -- they now name `just docker setup apply`, as
  do the missing-`.env.generated` error in `compose.sh` and the
  `BASE_IMAGE_DIGEST` comment in the shipped Dockerfile, and the `setup`
  doc comment now says the bare recipe prints its subcommands. The
  derived-figure lint now refuses a bare call of a recipe whose wrapper
  answers no argument with `usage`, read through the recipe body, the
  `init.sh` link and the wrapper itself.
- **three `just --list docker` descriptions named `just run` /
  `just start` / `just exec`, which a consumer cannot run (closes #1353)**
  -- the `run`, `start` and `exec` doc comments in `justfile.docker` now
  say `just docker run`, `just docker start` and `just docker exec -t
  <svc> bash`. The derived-figure lint now also judges the recipe doc
  comment (the comment line directly above a recipe) in every shipped
  justfile, quoted or bare.
- **an `ARG USER` with a literal default was told it has no default
  (closes #1348)** -- `ARG USER="initial"`, `ARG USER=initial`,
  `ARG USER='initial'` and a later `USER="initial"` in a multi-name `ARG`
  got the bare notice. The `arg_user` warning for such a line now names
  the default (`ARG USER defaults to "initial"`) and says the image builds
  that user, not the one compose passes. An empty or blank default
  (`ARG USER=""`, `ARG USER=`) counts as a default too, and the value is
  named byte for byte, boundary blanks and Unicode spaces included. A bare
  `ARG USER` keeps the base#1340 wording, a `USER_NAME` default keeps the
  may-run-as-root one, and every line warned on before is still warned on.
- **generated `.env` / `.env.local` / `config/.gitkeep` text and the
  shipped templates named `just setup` / `just build` / `just run`, which
  a consumer cannot run (closes #1349)** -- they now say `just docker
  setup` / `build` / `run` (and `just docker exec`). The Dockerfile
  comments that named `just test lint --home-literal` / `--arch-literal`
  now say those lints run in base's own CI. The derived-figure lint now
  also judges heredoc bodies under `dist/` and every line of the shipped
  `setup.toml`, `.setup.conf`, Dockerfile and `.hadolint.yaml`.
- **the reproducibility smoke skip and the DL3008 rationale told the
  user to run `just upgrade`, which no longer exists (closes #1341)** --
  the skip message in `test/bats/smoke/shared/reproducibility.bats` and
  the two DL3008 comments in `.hadolint.yaml` (symlinked into downstream
  repos) now say `just base upgrade`.
- **the bare `ARG USER` warning claimed the image builds its default
  user (closes #1340)** -- a stage built `FROM` a parent stage that
  declares `ARG USER` inherits that value, so the claim was wrong there.
  The `arg_user` warning for an `ARG USER` with no default now says that
  compose passes no `USER` build arg and that, unless a parent stage
  declares `ARG USER` (which this stage then inherits), the image does
  not get the user compose passes. It still names the line and the
  manual port, and is given on every line it was given on before.
- **the config summary listed setup.toml entries under INI-era
  `rule_N` / `arg_N` names (closes #1339)** -- the template's
  `[[build.args]]` printed as `arg_1 = APT_MIRROR_UBUNTU=...`, a name no
  setup.toml contains. Each entry now prints under its own
  `[[<section>.<array>]]` header (`[[volumes]]` at the root) with the
  file's field names (`key = ...` / `value = ...`), in file order
  across sections, an escaped header key included; an empty field
  prints as `value = ""`, an entry with no fields still prints its
  header, and numbered table scalars (`[image] rule_1`)
  print as the entries they stand for. Scalars print as before.
  `toml-bridge --kv` is unchanged.
- **`ARG USER` split over three or more lines of a long ARG was not
  warned about (closes #1336)** -- past 4096 bytes the `arg_user` scan
  looked for `USER` only within one line or two adjacent lines, so an
  `ARG` with a long default followed by `U\`, `S\`, `ER` was not matched
  and the upgrade printed no warning. It now also matches against the
  last bytes of everything joined so far, so a split over four or five
  lines is warned as may-run-as-root at the line the `ARG` starts on,
  also with blank or comment lines inside the split. The line-pair check
  is kept, so every warning it gave before is still given. The
  Dockerfile is still left unchanged.
- **auto-prune deleted a predecessor still tagged under another name
  (closes #1338)** -- after a rebuild moved a tag to a new image, the
  check for the old image's other tags used `docker images --filter
  reference=<id>`, which matches repo:tag patterns and never an image
  ID, so it found no tags and `docker rmi` ran: an old image left with
  one other tag (e.g. `bl-devel`) lost that tag and was deleted. The
  check now reads the tags from the image itself (`docker image
  inspect` by ID); a predecessor with any other tag is kept with
  `build_prune_skip_tagged`, and one with none is still pruned.
- **the `ARG USER` migration could leave the image running as root
  (closes #1322)** -- the rewrite of a bare `ARG USER` to
  `ARG USER="${USER_NAME}"` (#579) is retired: where `sys` creates the
  user from its own `ARG USER` and never declares `USER_NAME`, a
  rewritten stage could run as root. Migration `arg_user` now never
  changes the Dockerfile. It warns with the file and line for each `ARG`
  or `ONBUILD ARG` declaring `USER`, with lines joined as Docker joins
  them (`ARG US\` + `ER` counts), says the image may run as root when
  the default is `USER_NAME` or the line cannot be read, and states the
  manual port (`dist/dockerfile/Dockerfile:214`, `:298`, `:329`). A
  rerun repeats the warning.
- **the smoke-COPY migrations keep the retired prefix's dots literal
  (closes #1324)** -- the rewrite handed its escaped regex to awk with
  `-v`, which dropped the backslashes: an upgrade that ran the migration
  printed `awk: warning: escape sequence`, and a COPY such as
  `xbase/test/smoke/` was rewritten as if it named `.base/test/smoke/`.
  Such a COPY is now left alone, and passing the retired-prefix regex no
  longer produces the awk escape-sequence warning.
- **`setup apply` accepted an unknown table or a misspelt key without a
  word (closes #1328)** -- `[deploy] gpu_cuont = "1"` exited 0 and
  generated `count: all`. apply now reads each layer of the chain before
  writing anything and refuses a table no reader knows (empty ones too,
  via the bridge's new `--tables` view) or a key no reader reads (an
  empty array too, `[deploy] args = []`, via the new `--empty-families`
  view), with an
  ERROR naming the layer file and the table or `<table>.<key>`
  (`apply_unknown_table` / `apply_unknown_key`); `.env` and
  `compose.yaml` are left as they were. `[stage:<name>]` keys keep their
  per-stage allowlist WARN.
- **an upgrade's Dockerfile migrations keep each rewritten file's mode
  (closes #1323)** -- the migrations that rewrite a whole file left it at
  0600, so an upgrade turned a committed 100755 `script/entrypoint.sh`
  into 100644 in git. The file now keeps its mode. Repos already upgraded
  keep the mode they were left with.
- **the INI-to-TOML converter wrote the deprecated GPU-runtime key
  (closes #1327)** -- `_ini_to_toml_convert` carried `[deploy] runtime`
  into setup.toml verbatim, so the first `setup apply` after an upgrade
  warned about a key the upgrade itself had written. It now writes
  `gpu_runtime`, and a `[stage:<name>]` `deploy.runtime` as
  `deploy.gpu_runtime`. When the section names both, `gpu_runtime` keeps
  its own value and the legacy line is dropped (doc/deprecations.md). Each
  rewrite logs an `ini_to_toml_runtime_renamed` /
  `ini_to_toml_runtime_dropped` INFO. An existing setup.toml that already
  says `runtime` is not rewritten.
- **help text still described the INI era (closes #1326)** -- `just
  --list` named `setup.conf` for `setup` / `setup-tui`, and seven recipes
  (docker `help` / `start`, base `help` / `completions`, template
  `default` / `help` / `new`) listed the tail of a rationale comment. Each
  now has a one-line doc. `setup.sh --help` no longer says a bare call
  falls back to `apply` (it prints help), puts the `SETUP_*` drift
  metadata in `.env.generated` rather than `.env`, and describes the layer
  merge (including `set --local`) as key-by-key tables and whole arrays
  instead of section replacement.
- **a downstream repo's local tooling build no longer fails on a path only
  base has (closes #1172)** -- with `TEST_TOOLS_IMAGE` unset, `build.sh`
  built `test-tools:<version>` with the consumer root as its context, so
  `COPY dockerfile/toml_bridge.py` failed with "not found" in every repo
  carrying `.base/`. The context is now `.base/`. Repos that pin
  `TEST_TOOLS_IMAGE` (CI) are unaffected; base's own build is unchanged.

  reads it as the `[network]` table, but all three writers required `]` to
  be the line's last non-blank character. So `setup.sh set network.mode
  bridge` never entered the table: it appended a SECOND `[network]` and
  left the original value standing. TOML rejects a table declared twice,
  so a user who annotated their own setup.toml got a file nothing could
  read, from a write that reported success. One place now reads a
  header's comment off before any bracket matcher sees the line; the line
  is written back annotated.

- **the INI-to-TOML conversion reordered a numbered list (refs #1137)** --
  every reader of a numbered family sorts it by the numeric suffix, so an
  INI naming `rule_2 = @basename` above `rule_1 = prefix:docker_` tries
  the prefix rule first. An array of tables carries its order in the file
  instead, and the converter emitted blocks in file order: after
  migrating, `rule_2` was block 1 and `@basename` was tried first, which
  for `[[image.rules]]` changes the image name the repo builds under. Each
  family is now sorted by suffix before anything is emitted, read with
  `10#` so a zero-padded `rule_08` orders instead of dying as an invalid
  octal literal.

- **an emptied array could not be refilled (refs #1127)** -- `args = []`
  is an ordinary key and TOML refuses to extend one with `[[build.args]]`
  blocks, so the `add` that follows a removal answered `Cannot mutate
  immutable namespace` and the file stopped parsing. Both writers now
  re-decide such a declaration rather than copying it: remove-then-add is
  a round trip, a clear nothing refills survives a save, and an annotated
  declaration (`args = [ ]  # intentionally cleared`) counts as one --
  an operator who clears a list is the one who writes down why.

- **the migration's two machine-local backups were in neither ignore list
  (refs #1137)** -- the INI-to-TOML conversion renames `.setup.conf.local`
  and `.env.local` aside, and neither `.setup.conf.local.bak` nor
  `.env.local.bak` was canonical. Every other backup this tree writes is
  (`.env.bak`, `.setup.conf.bak`, `setup.toml.bak`), and these two carry
  what their ignored originals carried -- a per-machine override,
  `environment.env_N` credentials included -- so upgrading left the same
  secret reachable by `git add .` and shipped it in the Docker build
  context. Both are canonical now, which puts them in `.gitignore` and
  `.dockerignore` from the one list.

- **a literal-quoted table header was not a header (refs #1127)** --
  `['network']` is valid TOML and the bridge reads it as the table
  `network`, but `_conf_header_name` stripped basic quotes only. No
  writer recognised the section, so setting `network.mode` appended a
  second `[network]`: the same duplicate table a trailing comment
  produced, from the other half-recognised spelling.

- **the INI-to-TOML conversion renumbered a numbered family (refs #1137)**
  -- the converter skipped an emptied slot, so an INI carrying
  `mount_1 =` and `mount_2 = /data:/data` came out as ONE `[[volumes]]`
  block. The bridge numbers blocks as it meets them, so the extra bind
  became `mount_1` -- the workspace bind, whose clearing is the published
  opt-out -- and `_reconcile_workspace_path` honoured its existing source
  as a pinned path: WS_PATH silently resolved to the operator's data
  directory. Each family is now emitted dense from index 1 to its highest
  populated slot,
  an emptied slot as a FIELD-LESS block -- an empty body reads back as
  the bogus `":"` / `"="`.

- **a cleared list converted to an unspecified list (refs #1137)** -- an
  INI `[build]` whose only `arg_1 =` was empty emitted no
  `[[build.args]]` at all, which makes the key ABSENT -- the one state
  that is not a replacement -- so the key-level merge handed back all
  three args the template defines. Under the pre-ADR-37 INI chain
  `[build]` merged by section-replace, so that repo genuinely resolved to
  zero build args: the conversion changed behaviour against the
  operator's own prior config. A family with no populated slot now
  converts to the writer's own `path = []` declaration, placed by
  `_conf_toml_array_decl`.
- **a repeated INI key made the whole migration decline (refs #1137)** --
  an INI may name a key twice, and every chain accessor
  (`_conf_get` / `_conf_get_into`) resolves `[gui] mode = off` followed by
  `mode = auto` to the LAST occurrence. The converter emitted both, which
  TOML refuses (`Cannot overwrite a value`), so the commit gate declined
  the conversion: the INI intact and nothing lost, but declined again on
  every re-run, leaving such a repo unable to complete an upgrade until
  someone hand-resolved the duplicate. Repeated section/key pairs
  now collapse to the last occurrence, held at the position of the first.
- **the converter could move or drop a numbered entry (refs #1137)** --
  an entry of a TOML array IS the key `<name>_N` with N its plain
  position, so a suffix spelled any other way is read back under a
  different name: `[volumes]` whose only entry is `mount_01` had an
  EMPTY `mount_1` -- the published workspace opt-out -- and that path at
  `mount_1` afterwards, honoured as a pinned workspace with no warning.
  A suffix past 2^63 wrapped to 1 and jumped the queue; a populated `_0`
  has no 1-based slot; two keys at one index make the list readers count
  two entries where a key lookup reads one. All four now DECLINE by
  name, nothing written and nothing renamed. An EMPTY occurrence is none
  of them.

- **a section that emptied a list converted to one that never mentioned
  it (refs #1137)** -- the INI chain replaced a section WHOLE, so a
  `.setup.conf.local` naming `[security]` at all left the layer below
  with no `cap_add` entries. The converted file carried only the scalars
  it saw, and the TOML merge is key-level, so the list came back: an
  operator's narrowing of the container's capabilities undone by the
  upgrade that converted it. Every numbered family a section OWNS and
  populates nowhere now converts to the writer's `path = []`. A header
  with no entries owns nothing and still clears nothing.

- **`env_N` and `cap_drop_N` were collapsed like ordinary scalars (refs
  #1137)** -- neither had an array-of-tables home at the time (#1235
  later gave `cap_drop` one), so both stayed quoted scalars, and `_conf_list_sorted` is what reads them: it collects every
  non-empty entry and is not last-wins, so `[environment]` naming
  `env_1` twice is a TWO-variable list. The repeated-key collapse
  dropped one, in a file the parser accepts, with the INI already
  renamed to `.bak` -- and a dropped `cap_drop_1` is a container keeping
  a privilege the operator removed. A key shaped `<prefix>_<digits>` is
  no longer collapsed, so such an input is declined with both lines
  still on disk.
- **a clear that landed on a filled list entry went either way (refs
  #1137)** -- the ORDER of two occurrences of one index decides whether
  the two sides of a numbered family agree. `port_1 = 8080:80` followed
  by `port_1 =` is a disagreement -- the list readers keep the value, a
  key lookup reads the clear -- and now declines; `port_1 =` followed by
  `port_1 = 8080:80` is not, and converts to the one entry both sides
  answer. The first spelling of the check refused both, and an emptied
  slot whose suffix named no entry at all. `env_N` and, until #1235 gave
  it an array home, `cap_drop_N` -- read as a list but carried as
  scalars -- get the same two answers.

- **a one-sided array entry read back with its separator (refs #1234)**
  -- the writer splits an entry textually and the bridge joined the
  halves back unconditionally, so `HTTP_PROXY` came back `HTTP_PROXY=`,
  the OTHER build argument, and a port `80` came back `80:`, not a
  mapping compose accepts. `volumes` filtered on truthiness instead,
  which also lost POSITION: `/srv/data::ro` read back `/srv/data:ro`,
  mounting the host path at `ro`. The writer now omits a half the value
  does not have and the bridge joins the fields a block HAS -- except
  where they are ALL empty, which keeps the cleared-mount opt-out an
  empty value, not the bare `:` no list reader skips.

- **a converted layer stopped replacing a cap_drop list (refs #1235)**
  -- `cap_drop_N` had no `[[array of tables]]` home, so the converter
  carried it as a SCALAR, which merges key by key while the LIST it
  represents was replaced whole with its section. A `.setup.conf.local`
  naming `[security]` left the layer below with no cap_drop entries
  before ADR-37; after conversion those drops survived the replacement,
  so the container came out narrower than the layering asked for -- a
  surviving drop REMOVES a capability. Its two siblings there, read by
  the identical `_conf_list_sorted` call, had homes already, so
  `security.cap_drop` now exists too. `env_N` is unchanged: its
  destination is still open.

- **a negative zero read back as an unsigned integer (refs #1234)** --
  `_conf_toml_scalar` infers a type for a free-typed TABLE key, and its
  test was which text TOML ACCEPTS rather than which text reads back as
  itself. TOML takes `-0`, `+1`, `0x10` and `1_000` as integers and reads
  them as 0, 1, 16 and 1000, so `[environment] env_1 = -0` came back `0`
  -- the sign gone from a value the operator typed. Only `0` and a signed
  run of digits with no leading zero stay bare now; the other four are
  quoted, the same rule the array fields already follow. The template
  spells none of them bare, so no shipped value changes type.

- **a CONFIG_SRC redirect the text probe could not see authorised a
  destructive migration (refs #956)** -- the probe that decides whether
  the retired pip-helper line may be DELETED matched the file's TEXT, so
  every TOML spelling it was not written against read as "no redirect":
  a trailing comment after `key = "CONFIG_SRC"`, a quoted key, the scalar
  `arg_N = "CONFIG_SRC=..."`, and the inline `args = [{ key =
  "CONFIG_SRC", ... }]`. The upgrade then dropped a pip install that was
  working. A TOML layer is asked of the BRIDGE now, per layer so the
  three-answer status survives: a row is yes, a clean parse with no row
  is a provable no, and a parse that did not happen refuses the delete.

- **`--setup` on a terminal hit the frozen editor (refs #1148)** --
  `build.sh --setup` and `run.sh --setup` selected `setup_tui.sh`, which
  ADR-37 freezes until the migration completes, so both failed with
  status 2 before regenerating and before their main action: the one
  option whose job is "regenerate now" was the one that could not. Only
  the TTY path, which is why CI did not see it. They take `setup.sh
  apply` while the freeze holds.

- **a removal that changed nothing reported success (refs #1148)** --
  the commit gate asked only whether the rewrite PARSES, and a removal
  that did nothing leaves a file that parses with the value still in it.
  Both inline spellings slipped through: `resources = { shm_size = "64m"
  }` for a scalar and `args = [{ key = "FOO", ... }]` for an array are
  valid TOML the line-oriented writer cannot reach. The gate now asks the
  reader what the file SAYS -- a scalar must be gone, an array must be
  SHORTER, which is the question compaction leaves unambiguous and which
  says nothing about base#1233's open one. `setup.sh remove` also reads
  the writer's answer now instead of printing success over a refusal.

- **the template taught an `[environment]` spelling nothing reads (refs
  #1148)** -- its commented examples showed the direct-key form
  (`DISPLAY = ""`), which is ADR-37's destination for this section and
  whose readers have not landed: it parses and nothing emits it.
  `_resolve_docker_conf` collects `env_N`, so the examples now show that
  form and say which is which.

- **an annotated opt-out left the wrapper transcript recording (refs
  #1148)** -- `_transcript_conf` is a source-time grep by design (the
  bridge would put a `docker run` in front of every wrapper), and it
  returned the whole right-hand side. `wrapper_transcript = false #
  disable capture` read as `false # disable capture`, matched neither
  boolean, and recording stayed on against an explicit opt-out -- and an
  operator who turns capture off is exactly the one who writes down why.
  A quoted value and a quoted key were invisible the same way. All three
  spellings read correctly now; a `#` inside a quoted value is still
  content.

- **a documented tmpfs size never reached compose (refs #1148)** -- the
  template teaches `[[tmpfs]]` as `path = "/tmp"` with `size = "64m"`,
  and the bridge's serializer read only `path`. The size never reached
  `tmpfs:`, so following the template gave Docker's default limit instead
  of the 64 MB asked for. The two fields are joined into the one string
  the compose emitter consumes, so the template's spelling and the
  converted `path = "/tmp:size=64m"` now answer alike. No size is still
  no suffix, not a bare separator.

- **`setup add` treated an unreadable configuration as an empty one
  (refs #1148)** -- the effective view is what tells `add` which slot to
  append at, and a FAILED read was taken as a list with no entries: the
  search found nothing, chose index 1, and the write landed on top of
  whatever was there while reporting `add [build] arg_1 = ...`. Reachable
  with a valid target over an unparseable layer below it, which the
  writer's own commit gate does not catch because the file it writes
  parses fine. `_conf_load_layers` already refuses to report an empty
  configuration as a loaded one; `add` now stops on that instead of
  inheriting the silence, before any write.

- **a value's leading and trailing tabs were read away (refs #1148)** --
  the transport carries a tab inside a value deliberately: it is the last
  field of the row, so it arrives intact. Both readers then split with
  `IFS=$'\t' read -r a b c`, and a tab is IFS whitespace, so it was
  stripped from the ends of the field and runs of it collapsed.
  `[environment] env_1 = "TOKEN=abc<TAB>"` loaded as `TOKEN=abc` --
  a container value the writer had preserved, changed with nothing said.
  Both readers split at the first two tabs now and keep the rest byte for
  byte.

- **`setup add` replaced the list it was appending to (refs #1148)** --
  an array is replaced whole by the highest layer that defines it, so a
  file that declares one owes the FULL list. `add` chose its slot from
  the target file's own section whenever that section had any key -- true
  under the old section-replace, false now. A repo `setup.toml` carrying
  only `[build] network = "host"` inherits the template's three build
  args; `add build.arg FOO=bar` wrote an array of one and the mirrors and
  timezone were gone. It now reads the merged layers at or below the
  target and materialises the inherited entries first -- at or below, so
  a repo write never copies the gitignored local layer down.

- **an index with no slot landed in slot 1 (refs #1148)** -- the writer
  addresses an entry of a numbered family by POSITION, and accepted any
  run of digits as one. On the shipped template `setup.sh set
  volumes.mount_0` and `set volumes.mount_01` each wrote a block that
  read back as `mount_1`, the workspace bind, so a key the operator typed
  became the one slot that redirects WS_PATH. The converter already
  declines both shapes by name; both writers now do too, before any temp
  file exists.

- **per-service logging settings were dropped by spelling (refs #1148)**
  -- the service set was matched off the physical `[logging.<svc>]`
  header text. A trailing comment after the bracket is part of a valid
  header, and an inline `runtime = { ... }` inside `[logging]` is the
  same table; the bridge reads both as `logging.runtime` and the matcher
  saw neither, so that service's driver, rotation and host-log mount
  settings vanished from the generated compose with nothing said. The set
  is derived from the merged parsed sections now -- which is also the
  cross-layer union the code was written to build, in one read instead of
  one per layer.

- **a newline in a TOML value truncated what the shell read (refs
  #1148)** -- the bridge's KV stream is line- and tab-delimited, and both
  delimiters were emitted raw. `watchdog_check = "echo first\necho
  second"` is an ordinary TOML string: the shell read
  `watchdog_check = echo first` and took `echo second` as a SECTION, so
  the watchdog ran a truncated command and nothing failed. A tab in a
  quoted key shifted the split the same way. Both are refused by name
  now, the answer the writers already give at the other end of the pipe.
  A tab in a VALUE still passes -- the value is the last field, so it
  arrives intact.

- **array settings vanished from the build/run summary (refs #1148)** --
  `_print_config_summary` read the file's lines through the INI-only
  `_dump_conf_section`, which matches an exact `[section]` header and
  stops at the next one. Against a real `setup.toml` that lost every
  numbered family: an `[[volumes]]` block is not inside `[volumes]`, and
  `[build]` ended at the first `[[build.args]]`. Mounts, devices, build
  args, ports and capability lists were all missing from the one screen a
  first-time user reads before a build. It reads the resolved view now,
  loaded once.

- **a TOML write could leave a file nothing can read (refs #1148)** --
  two more shapes the line-oriented writers could not edit. A
  literal-quoted key (`'mode' = 'host'`, valid TOML) was not recognised,
  so `setup.sh set network.mode bridge` appended a duplicate the bridge
  refuses; and a value spanning physical lines had only its FIRST line
  replaced, orphaning the rest. Both reported success and left an
  unreadable file. The key matcher now takes both quote forms, and --
  because patching the fifth shape leaves the sixth -- both writers
  promote a rewrite only once the shipped bridge has parsed it, the
  converter's own gate. A refused write leaves the file unchanged.

- **the env override guidance named a file nothing reads (refs #1163)**
  -- `_scaffold_env_local` writes `.env.local`, which compose reads as a
  dotenv file, and its instructions told the operator to put
  `key = "value"` under a TOML `[environment]` table there; the generated
  `.env` header pointed at `.env.local.toml`, which nothing reads until
  base#1168 lands the TOML readers. compose does not refuse such a file,
  it improvises -- the header line is skipped and `[stage:headless]`
  arrives as a variable named `[stage` -- so following the guidance gave
  no error and no override. Both files are back to `KEY=VALUE` and name
  only the files the `env_file:` list loads.

- **an emptied array was a local override nothing could see (refs
  #1148)** -- `_setup_conf_local_sections` answers "which sections does
  the gitignored local layer define", and it read the layer's ENTRIES. An
  array declared with NO entries emits no bridge row, so a
  `setup.local.toml` carrying only `[build] args = []` reported no local
  sections while clearing the template's three build args through the
  merge. `setup deploy` then built a field bundle from untracked
  configuration: its refusal did not fire and its README named no section.
  The declarations are now read beside the entries, root-level and
  annotated spellings included.

- **a write past the end of an array landed in slot 1 (refs #1148)** --
  index N of a numbered family IS the key `<prefix>_N`, and the TOML
  writer appended ONE block whatever index was named. On the shipped
  template, whose `[volumes]` holds no block, `setup.sh set
  volumes.mount_2 /data:/data` read back as `mount_1` -- the workspace
  bind -- and `_reconcile_workspace_path` honours an existing absolute
  source there as a deliberately pinned workspace, so WS_PATH silently
  became the operator's data directory. The INI writer wrote the key
  `mount_2` and left `mount_1` absent. Intervening positions are now
  padded field-less, the rule and the spelling the converter's dense
  emission already uses.

- **a narrowing flag the table does not carry read as one that does (refs
  #1226)** -- `just test lint --log-event-registry` sat in the justfile's
  narrowing list beside the twenty-one flags that DO narrow the bare
  phase, and the sentence closing that list generalised over it: "the
  behaviour matches the bare `lint`". The scan is a manual tool, so there
  is no bare-phase behaviour to match. The flag dispatches and exits 0 --
  the divergence was entirely in the prose. The line now says so, and
  ci_spec holds the whole list to `_LINT_TOOLS`, to the stated untabled
  entry points and to `_run_lint_tool`'s case labels, so the next
  advertised flag nothing backs is a red test.

- **`remove volumes.mount_1` handed the workspace position to another
  mount (refs #1148)** -- removing an array entry compacts the ones after
  it, and slot 1 of `[volumes]` is the workspace bind by POSITION and
  nothing else. With the promoted bind's source present,
  `_reconcile_workspace_path` read it as a pinned workspace and warned
  about nothing, so WS_PATH resolved to the operator's data directory;
  absent, it WARNed and overwrote that bind with the portable workspace
  mount. The save is declined now and names the CLEAR instead -- the
  published opt-out, which moves no slot. Only the promoting case is
  refused: the sole mount, or any mount above slot 1, still removes.

- **`just test coverage-path` re-read the flags it forwarded (closes
  #1284)** -- the body interpolated `{{args}}`, which `just` expands as TEXT
  before the recipe's shell sees it, so `--filter 'bare invocation'` reached
  the runner as two arguments and `--filter 'foo|bar'` became a shell
  pipeline, dying at 127 with `bar: not found`. It forwards `"$@"` now, as
  `mutation-probe` and `bats-path` already did; the sweep was derived, so
  `lint`, `smoke`, `stop` and `sync-readme` moved with it. The static guard
  asserted `--coverage-path '{{spec}}'` -- it PINNED the defect -- and now
  refutes any `{{` there, beside an executed arm comparing the recorded
  arguments by equality.

## [v0.43.0-rc2] - 2026-09-06

### Added

- **ADR-00000035: `compose.yaml` stays at the repo root, and a test has a
  LEVEL and a TYPE** -- the compose file is not CI-only, and stays at the root
  because Compose derives the project name from the config file's DIRECTORY.
  The taxonomy half re-states ADR-00000018's two axes: `smoke` is a TYPE, not
  a retired level; its directory reflects WHEN it runs, not how much it covers.
  Also corrects a duplicated 00000030 row in the ADR index -- the entry-point
  record is 00000032.

- **the `[Unreleased]` category set is locked, and the split changelog has a
  lint (refs #926)** -- `changelog_categories.sh` is the one definition of the
  seven categories (BREAKING plus the Keep a Changelog six); the
  changelog-entry lint refuses any other heading in `[Unreleased]`, and fails
  if `CONVENTIONS.md` stops printing it. Released sections keep the headings
  they shipped with. The `changelog-layout` lint pins where a section, its
  compare link and `[Unreleased]` live, refuses a second copy of either,
  re-derives the index, and refuses a `## [` section anywhere but a series
  file, the index included. Affects anyone writing a base changelog entry.

- **a full-scope coverage run can use the whole machine (closes #726)** --
  `just test coverage-local [N]` (default `nproc`) runs the same specs
  `just test coverage` runs, as N concurrent kcov processes over the shared
  partition, merged into one report: **34 minutes to 5 on 32 cores**. It
  stamps `scope=full`, so `just release coverage-badge` accepts it. A slice
  that produced no report fails the run rather than merging to a smaller
  total. Caveat, measured: its covered set is 27 lines (0.33%) below the
  serial run's, because the suite covers slightly different lines depending
  on the order it runs in -- ADR-00000008's Measurement. **The PR gate is
  unchanged.**

### Changed

- **`lint-static` runs as four derived groups, not twenty one-lint jobs
  (closes #1071)** -- the 20 jobs each paid a runner startup to do a few
  seconds of work, and took concurrent slots from the coverage shards, the
  run's critical path. Four groups: no partition beats its longest driver,
  and four is the smallest count whose even share falls under that floor.
  The partition is round-robin and cost-blind, so the slowest group is that
  driver plus its neighbours -- above the floor, not at it. Membership is
  computed from `_LINT_TOOLS` by `test.sh --lint-group N/T`, so a new lint
  joins a group with no workflow edit. A checks-list entry names a group;
  its output names every lint that failed in it.
- **the bats job count is a floor on concurrency, not the core count
  (closes #1068)** -- `$(nproc)` answers a CPU-bound question and this suite
  waits on subprocesses: on CI's 4-core runner `--jobs 4` measured no faster
  than serial. Now `max(cores, 32)` -- a floor, not `k x nproc`: 32 is the
  knee (16 jobs cost 1.65x, 32/64/128 are within 3% of each other), and only
  a floor cannot land under it. 1.75x on a 4-core coverage shard, 2.1x on
  plain bats. The two kcov runners hold at one job per core under a new `metered`
  policy: more jobs there loses a reproducible 31 covered lines to kcov's one
  parser (#726). And a failed `nproc` no longer prints the label a genuine
  4-core reading prints.

- **a coverage SHARD now runs its bats in parallel under kcov (closes #1060)**
  -- `_run_coverage` was the one bats invocation in `drivers/bats.sh` that
  never took the `--jobs` every other runner gets from `_bats_args_with_label`;
  `_run_system`, the other hand-built one, uses it too. Shards 1/8 and 6/8 go
  147s -> 50s and 371s -> 196s; seven of eight parallel runs reproduce the
  serial covered set, the eighth missed 3 lines. A run walking the
  WHOLE suite stays serial, `1/1` included -- the policy follows the walked
  set, not the argument -- because parallel there records a strict subset
  (8617 vs 8532) and would move the release badge. Affects CI wall time;
  `just test coverage` is unchanged.

- **`doc/test/TEST.md` and `doc/test/unit.md` record no suite total any more
  (closes #978)** -- an aggregate over the working tree names nothing it
  measured, so it is wrong between every commit and its resync, and its five
  lines were the ones every branch rewrote. Replaying the 64 PRs opened since
  2026-08-25 against today's `main`, 57 conflict in `doc/test/`, and 52 of
  those conflict in `TEST.md` on those lines alone. Ask `just test` instead.
  The per-spec `(N)` headings and the per-test rows STAY: #999 made them
  generated from the specs' `# why:` markers, so they cost no sync step.
  The sibling catalogues name the self-test suite, not the gone figure.

- **`just release coverage-badge`'s refusals now name both whole-suite
  runs (#726)** -- every refusal that asks for a re-run costs the operator
  the most expensive run in the repo, and the remedy sentence named only
  the serial one. It now offers `just test coverage-local` beside it, from
  a single shared hint rather than five copies. Affects anyone who has hit
  a badge refusal: the faster route is now in the message.

- **an ADR's trigger claim may now name any real trigger, not only
  `workflow_call` (#726)** -- the `adr_doc_claims` rule read its escape
  hatch as one literal string, so the first record describing a
  `workflow_dispatch`-only workflow was reported for saying something true.
  The accepted trigger is now read off the workflow's own `on:` block, and
  the code span must BE it -- `gh issues list` no longer excuses a claim
  about an `issues`-triggered workflow. A `tags:` key that is not a push
  filter, such as a `workflow_dispatch` input named `tags`, no longer reads
  as a tag trigger either. Affects anyone writing an ADR that names a

- **a coverage job count written with a leading zero is now refused
  (#726)** -- `010` passed the `^[0-9]+$` validator and was then read in

  run instrumented 8 slices of a 10-way partition, merged them, and
  reported the result as the whole suite. Affects anyone zero-padding a
  count -- `just test coverage-local 010` now refuses, on the host and
  again inside the container, instead of publishing a figure with two
  bins missing from it. Plain counts are unchanged.

- **a flag combination is now checked before `test.sh` answers a query
  (#726)** -- `--jobs` with no `--coverage-local` is refused because a

### Removed

### Fixed

  three gate cycles, and none of them said how many remained. Each driver

- **an upgrade now commits what it rewrote (closes #1036)** -- a

  statement; anywhere else -- including after a `;` or an `|| true` ANYWHERE
  in it, continuation lines included -- the negation is computed and discarded
  while the case name still claims the property. `&&`, and any `||` whose
  operand CAN fail, are exempt; the spec pins both by running them. Quoted
  text and trailing comments are not separators. The population is WALKED (the
  shipped `dist/test/bats/smoke/` tree counts), and an unopened header or an
  unclosed body fails the lint.

- **`errexit-bang` judges the FOLDED statement, so a substitution spanning
  lines is read as one (refs #956)** -- a `$(` opened on one line and closed on
  the next was scanned at depth 0 on the continuation, where a `#` opens a
  comment and everything behind it -- separator included -- was dropped.
  Physical lines are now folded while a `\` continuation, a quote or a `(` is
  still open, and the scan runs once over the whole statement. A statement
  still open where its body closes is reported when it is a `!` one or when it
  folded a line opening with `!` into itself; otherwise it is unreadable but
  hid nothing this rule judges.

- **`errexit-bang`: a statement ends where bash says, not where the line ends
  (refs #956)** -- a `\` glued to a WORD splices: `! grep -q A\` over

  old per-line test read. A line ending in `|`, `||`, `&&` or `|&` is
  INCOMPLETE, so `! cmd ||` over `true` is the one `|| true` the lint names in
  its own message -- and the same split over `&&` or `|` no longer reports the
  body's own last statement. The unreadable-fold row is now silenced by the
  allow region, like every row that judges a `!` line. What stays unmodelled is
  listed in the driver with the direction each errs in; #990 and #991 track it.

  #956, closes #989)** -- the fold above reads a line ending in `|`, `||`,
  `&&` or `|&` as incomplete, but whether the logical line was a `!` statement

  `! grep -q A f; true` was judged by no rule at all: 30 real violations that

  the `||` in front of it stays the `echo`'s, and the row names the line the
  `!` opens on. `! A ||` over `! B` is still one list.

- **`errexit-bang`: a `!` RIGHT operand is exempt from errexit too (refs
  #956)** -- the live-`||` exemption rested on "B's failure is not exempt from
  errexit either", which bash contradicts when B is itself `!`-inverted:

  `! A || ! B` outside the body's last statement aborts nothing -- the one
  inert shape the exemption covered. It is now declined whenever a RIGHT operand

- **the errexit-bang lint's three named misses (closes #990, #991, #992)** --
  a CRLF `*.bats` is REFUSED by name (a `\r` disarmed the line continuation,

- **`just upgrade` no longer deletes a working pip install from a consumer
  Dockerfile (refs #956)** -- the migration dropped every `pip install -r
  ${CONFIG_DIR}/pip/requirements.txt` line as base's empty placeholder, but
  that line is byte-identical whether the overlay holds the placeholder or a
  real list. It resolves the config source first -- a `CONFIG_SRC` redirected
  by the Dockerfile or by ANY `.setup.conf` layer points the install elsewhere
  -- and deletes only where the file is PROVED inert: OBSERVED absent, or read
  end to end and nothing but blanks and comments. A file, a directory or a
  conf layer the check could not read answers "unknown", never "empty", and

- **the bang lint dropped the statements it had opened, and flagged two shapes
  that were never violations (refs #956)** -- a `!` statement whose
  continuation line was followed by a BLANK or a comment line was judged by
  neither rule: the skip for those lines sat above the point where a statement
  is judged, so the open statement was discarded by the next real line and
  nothing reported it. They now END the statement they follow. Two false
  positives go with it: a separator inside `( ... )` is the argument's, not the
  statement's, and a `#` opens a comment wherever the shell opens one -- after
  `;`, `&`, `\|`, `(` and a subshell's `)`, as well as after a blank.

- **the bang lint now refuses a backgrounded assertion, and stops cutting a
  line at a `#` that follows a quote (refs #956)** -- `! cmd &` is an async
  list: the fork's status is 0 whatever the command did, so the assertion
  cannot fail its test even as the body's LAST statement, the one position the
  rule declines to judge. It is reported now, with `&&`, `\|&`, `>&` and `&>`
  excluded by the operator they belong to rather than by a roster. Separately,
  a closing quote and a backslash escape do not end a WORD, so the `#` in
  `! grep -q 'a'#b f; true` is data and the `;` behind it is real: the scan
  stopped reading such a line as a comment and dropping the separator.

- **the bang lint no longer cuts a line at a `#` behind an expansion's `)`
  (refs #956)** -- a `)` ends a WORD only where it closes a SUBSHELL:
  `printf '[%s]\n' $(echo A)#b` prints the one argument `[A#b]`. Reading every
  `)` as a word end made the `#` in `! grep -q A $(echo z)#b f; true` a comment
  and blanked the `; true` behind it -- a dropped violation. The `(` at depth 0
  now records whether it opened a subshell or an expansion (`$(`, `$((`, `<(`,
  `>(`) and its `)` reads that back. A `)` whose `(` this per-line scan never
  saw ends no word either, so a shape it cannot account for can only make the
  lint over-report, never discard a line.

One item may list several candidate paths, so both smoke layouts serve one workflow.

- **`changelog-entry`: the lint could report clean while measuring nothing (refs #917)** -- four ways it did. An entry quoting the marker syntax, e.g. `<!-- changelog-entry-lint: allow-begin -- why -->`, was read as an unclosed region and skipped every entry after it; a `## [` inside a fenced example moved the scanned section; a `*`, `+` or indented bullet reported "holds no entries"; and the length was characters or bytes depending on the caller's locale. Affects anyone adding an entry: unrecognised bullets now fail by name, and the clean line reports how many entries it checked and how many an allow region suppressed.

- **`just docker build test` reported success whether the checks ran or were CACHED (closes #882)** -- a `-test` stage asserts by RUNning shellcheck / hadolint / bats as build layers, so a cache hit reproduces it without executing one of them, and the wrapper printed the same thing either way. Verification targets (`test`, `<stage>-test`, `smoke`) now report per step which checks executed and which were CACHED; an all-cached build says in words that it is not evidence the checks pass. An output the report cannot read exits non-zero rather than reporting a pass. Consumer-visible: those targets pin `BUILDKIT_PROGRESS=plain` and their build output now arrives on stdout.

- **`just docker build <stage>-test` no longer fails a consumer stage that verifies its own way (refs #882)** -- a check was defined as a RUN naming bats / hadolint / shellcheck, so a Playwright gate, a heredoc `RUN` or the template's own `RUN bash -c "${RUNTIME_SMOKE_CMD}"` exited 1 on a build that succeeded, while `apt-get install shellcheck` counted as a check that ran. WHICH steps are reported is now decided by the stage and ran-vs-CACHED by the progress state; each is named by the command it invokes. A stage with no RUN step warns instead of failing, and only output carrying no BuildKit progress exits non-zero. The shipped `devel-test` reports 4 steps, not 3.

- **a `v0.41.0` consumer half-upgraded to `v0.42.0` and lost `just` entirely (closes #915)** -- an upgrade is driven by the consumer's OWN vendored `upgrade.sh`, which resyncs by calling `init.sh` at the repo root; the `dist/` reorganisation moved that file and left nothing behind. The subtree pull commits before that step, so the upgrade died at exit 127 with `.base/.version` claiming `v0.42.0`, `git status` clean, and `justfile` plus every `script/*.sh` wrapper dangling. A repo-root `init.sh` forwarder restores the name, not the layout. A repo that already hit this is only un-resynced: run `./.base/dist/script/base/init.sh` and commit.

- **the same upgrade then left a Dockerfile that could not be built (refs #915)**
  -- the `dist/` move deleted `.base/config`, `.base/script/...` and
  `.base/test/smoke/`, and no migration rewrote the flat layout every deployed
  consumer is on, so the upgrade reported success and the next `just build`
  died on its first `COPY`. The migration list now rewrites those paths and
  splits the smoke COPY into the shared plus per-stage `dist/` folders, and
  `init.sh` applies it on every resync -- the one current code path an OLDER
  vendored `upgrade.sh` runs. Repairs a repo already broken this way:
  `just base init`.

- **a failed upgrade no longer leaves the subtree pull committed (refs #915)** -- rollback fired from one place only, so a failure in any later step aborted with the pull already in history. An EXIT trap now covers the whole post-pull window, armed the moment the pull commits and disarmed after the last failable step -- before the advisory drift warnings, so a warning can never undo a landed upgrade. Half-upgraded becomes unchanged-with-an-error. Resetting is safe precisely because git-subtree refuses a dirty tree, so everything present afterwards was made by this run; the reset is paired with a sweep of files that became untracked during it.

- **the released-tree fixture is resolved only by the runs that read it (refs #915)** -- `prepare-prev-release.sh` ran ahead of EVERY compose dispatch, so a shallow, tagless or offline checkout could not run `--bats-unit-shard`, `--bats-fragile` or a coverage shard at all, and a failed tag fetch turned a CI job red for a reason naming nothing it runs. It now runs only when the dispatch about to start executes `prev_release_upgrade_spec.bats`, asked of the same shard / fragile selectors the container uses -- a shard slice really can carry that integration spec. For those runs an unresolvable fixture is still fatal before any container starts.

- **an under-declared release-archive manifest entry is no longer read as an absent path (refs #914)** -- an optional entry whose `<paths>` column was empty, whitespace-only, or missing from a short line resolved as "found nothing", which is how a legitimately absent path resolves: the release cut, the item was archived by nobody, and the log named a blank path. A line that is not five non-blank columns is now a config error (exit 2), in `--list` as well as in assembly. The specs that guard the payload assert against the parsed entries instead of searching the file, so deleting an entry while leaving its comment goes red. Affects maintainers editing `script/ci/release/archive.manifest`.

- **`setup.sh set` no longer writes a duplicate key when the value carries an inline ` #` (refs #955)** -- the in-place writer skipped any existing line containing a space-then-hash as if it were a comment, so a legitimate value such as a `lifecycle.watchdog_check` shell command never matched its own key: the replace was skipped and a second `key = ...` was appended. Reads are last-wins, so behaviour looked right while `.setup.conf` collected a stale duplicate on every write. The writer now decides "comment" the way the reader does -- `#` as the first non-blank character.

- **a per-service `[logging.<svc>]` override no longer leaks a bogus line into `[logging]` (refs #955)** -- matching an override key to its section by dot-split prefix cannot tell section `logging` + key `web.driver` from section `logging.web` + key `driver`. TUI Save injected `web.driver = ...` into the parent, `add logging.<svc>.<list>` appended its slot there, and `show <section>` / `list` listed the per-service value under the parent -- `list` twice, so piping that documented output back rebuilt the bad file. `show logging.<svc>` now reads the sub-section instead of erroring. Only `.setup.conf` was affected. One owner now holds the split: `set` / `show` / `list` / `remove` / `add`.

- **a `[stage:*]` service now resolves `${VAR}` env cross-references the way the shared `.env` does (refs #955)** -- the standalone per-stage `environment:` block quoted the stage's own entries but skipped the sibling expansion `write_container_env` runs, so one `setup.conf` produced two container envs: `/foo/production/lib` from `.env` and a literal `/foo/${BUILD_TARGET}/lib` on the stage, which compose's substitution layer cannot resolve from a sibling entry. Expansion reads the full effective list so a reference to an inherited sibling resolves; only the stage's own tail is emitted. Affects any `[stage:*]` override whose `[environment]` cross-references another entry.

- **`just base completions install --shell` with no value fails instead of hanging (refs #955)** -- `shift 2` with one positional left fails and shifts nothing, and the `|| true` swallowed it, so `$1` stayed `--shell` and the argument loop spun forever. It now requires its value the way the sibling `--lang` already did: a usage message and exit 1.

- **the #955 guards now fail when the property they name breaks (refs #955)**
  -- three could not. The dot-prefix guard scanned hand-listed paths and ended
  in a bare `assert_failure`, so a renamed path (grep exit 2) read as a clean
  scan. It now derives its population -- root `dist/`, every file whose CODE
  calls `_load_setup_conf_full` / `_setup_effective_full` -- asserts that
  floor, and pins grep to status 1. Its glob reads the quotes around the
  literal dot as a CLASS, so the same defect spelled `${_sec}'.'*` is now
  visible; its name and comment state what it still does not check. `show
  logging.<typo>` is pinned to the KEY error KIND, and the dump specs pin the
  section header. Test-only.

- **a failed `init.sh` resync no longer leaves the consumer's files half-rewritten (closes #937)** -- the resync rewrites the `Dockerfile`, `.gitignore` and the wrapper symlinks inside an upgrade that has already committed the pull, and whether a partial rewrite was undone depended on the caller: the current `upgrade.sh` has a trap, the vendored `v0.41.0` copy every deployed repo runs has none. `init.sh` now snapshots the roots it writes into -- a hand-written `.env` included, which no `git reset` could return -- and restores them itself, staged index removals and all, without touching history. A restore that does not fully work exits 1 naming the tree as NOT restored.

- **the shipped Dockerfile now records what it was built from (closes #951)** --
  `BASE_IMAGE` defaults to the moving `ubuntu:24.04` and the apt layers carry
  no versions, so two builds of one template version differed silently. The
  default stays moving; every image now writes
  `/usr/local/share/base/base-image.env` and `packages.txt` after each apt
  layer and carries the OCI `base.name` / `base.digest` labels. A `LABEL`
  cannot branch, so the annotation passes `BASE_IMAGE_DIGEST` through instead
  of deriving one. A digest-pinned `BASE_IMAGE` alone builds -- no stage
  refuses it, `runtime-base` included -- leaving that field empty in both
  sinks; only a contradicting digest arg fails, in `-test`.

- **a spec no longer passes when the artifact it asserts on is deleted (closes #953)** -- 54 guards across 14 spec files opened with `[[ -f "${SUBJECT}" ]] || skip`, which cannot tell "absent by design" from "renamed and nobody noticed" and answers the second with a green run: renaming `build-worker.yaml` turned 52 assertions into `ok ... # skip` and the suite still exited 0. All 54 guards now fail through `assert_spec_subject`, naming the path. Every surviving `|| skip` guards a capability and now has a fail-closed counterpart -- the last was the tooling image's compose plugin, now pinned statically. The invariant itself proves it scanned, and knows the `[ -f ]` / `test -f` spellings.

- **the shard-balance guard failed CI on a partition that was fine, and could never fail locally (closes #940)** -- its total was summed over `test/bats/unit/` while `_shard_unit_files` partitions unit **+** integration, so the average was short by every integration spec, condemning a healthy partition. A latent second defect: it counted `@test` lines while the partitioner weighs recorded seconds, which collapse to one number locally. The probe now measures through `_spec_weight` against the bound no partition can beat, over the eight shards CI runs rather than four; synthesised weights drive skewed distributions locally, and a case asserts the probe's total still spans the whole pool.

- **three test guards now cover the property they are named for (refs #962)** --
  the fail-open `|| skip` invariant knew `[[ -f ]]`, `[ -f ]` and `test -f`
  only, so a negated check, an `-e` / `-s` / `-d`, a `-L` on a wrapper symlink,
  or the two-line form every surviving skip in this suite uses all stayed
  green. Any one-letter unary test now matches, and the scan rejoins a
  continuation before matching; widening it found two live
  `[[ -d "${WF_DIR}" ]] || skip` guards, now fail-closed.
  `self_test_yaml_spec`'s block extractors read the shared comment-stripped
  view, so a comment in `ci-rollup` no longer satisfies an assertion about
  what the job runs.

- **three template guards passed while the property they name was broken
  (refs #951)** -- the apt-layer scanner read a `<<<` here-string as a heredoc
  (awk matches leftmost, so it found a `<<` at the second `<`) and swallowed
  every layer below it into one block, hiding an out-of-order manifest refresh;
  the case above it asserted a block count, which is the same number either
  way. The disproven-claim sweep derived its directory roots but named its only
  top-level file, exempting `init.sh`, `justfile`, `compose.yaml` and
  `CONTEXT.md`. Its marker guard counted `begin` against `end`, calling an
  inverted pair balanced while the file tail is excised anyway.

### Documentation

- **ADR-00000027: a Z release is cut automatically and one per bug, X/Y stay
  the maintainer's, and only X/Y fans out** -- policy behind `semver-bump` /
  `/release`, not a new mechanism. A `vX.Y.Z` (Z>0) needs no ACK, restoring the
  skill's own table, and one bug is one release so a downstream can name the
  tag carrying its fix. The binding half is classification: a fix that changes
  behaviour is a Y whatever it is labelled. #927's fanout triggers on X/Y
  **only**, because `just base upgrade <tag>` is one subtree pull to that tag,
  so a Y delivers every Z in between and only the notification is batched.
  Affects anyone cutting a base release.

- **ADR-00000028 + PRD invariant 10: documentation is derived from the code,
  never duplicated beside it** -- the record only; the mechanism is a separate
  change. A figure computable from the tree is not stored in a tracked file
  somebody must keep in agreement with it, so test statistics leave
  `doc/test/*.md` and exist only in a release, rendered from the JUnit XML the
  tag-push run already emits. The record separates this from PR #943, which
  removed a hand-built *source* archive GitHub already produces. Affects anyone
  editing `doc/test/`, and invariant 2's guard list, which loses the doc-count
  drift gate when the mechanism lands.
